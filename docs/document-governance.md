# ドキュメント管理方針（共同確認案）

本書は文書の配置・読み順・正本の判定方法を決める提案であり、個々の製品仕様や AWS 実環境を確定するものではない。AI 開発ルールは [AGENTS.md](../AGENTS.md)を正とし、文書の配置・状態・保管は本書、PR と実装の同期手順は[AI 駆動開発の運用](ops-ai-driven-dev.md)を正とする。

## 1. 採用する構造

- 物理配置は浅いディレクトリを維持し、[spec.md](../spec.md) と目的別索引から現行正本へ案内する。文書本文を索引へ複製しない。
- 「なぜ作るか」「何を守るか」「今どう動くか」「どう運用・改善するか」「なぜ変えたか」を別の読み口にする。同じ文書は複数の入口から相対 Markdown リンクで参照できる。Obsidian 固有のリンク形式を正本には使わない。
- `docs/product/`、`docs/operations/`、`docs/improvement/` 等は必要な入口が定まった段階で追加する候補であり、本提案だけを根拠にフォルダを増やしたり、全ファイルを移動したりしない。

| 知りたいこと | 現在の参照先と位置づけ | 次の整備 |
| --- | --- | --- |
| なぜ作るか・誰の判断を支えるか | [製品意図](PRODUCT_INTENT.md)はドラフト。合意済みの中核は根拠を集めて違いを示し、人の判断を支えること。RAG の既決前提は[検索原則](../.cursor/rules/rag-search-principles.mdc)と[RAGのニュアンス](decisions-2026-07-29-rag-nuance.md)を参照し、合意済みの前提と将来の仮説を区別して読む | 製品・業務の入口から合意済み／未決を区別して案内する |
| 利用できる資料・機種の境界 | [取扱機種の決定記録](decisions-2026-08-21-model-scope.md)は決定時点の根拠、[RAG API](api/rag.md)は現在の契約 | 境界変更は双方の PR 確認を経て、現行仕様と決定記録の関係を示す |
| 現在の API と機能 | [API 仕様](api/rag.md)とコードを突合する。[Phase 2 機能仕様](features/production/phase2-rag-chat.md)には実装との乖離を示す警告がある | 機能仕様の全面再検証・更新は別途事前確認して行う |
| 運用・復旧 | [運用ランブック](ops-runbook.md)は試行運用のドラフト。デプロイ構成の[旧文書](deployment.md)は `legacy` | 実環境と照合して現行手順を確定する。旧文書を現行手順として案内しない |
| どう改善するか | [評価手順](eval-2026-07-29-retrieve-golden-set.md)と[評価の落とし穴](decisions-2026-07-29-layer1-eval-ops.md)をセットで読む | 現場の失敗から評価・採否・実環境確認までの入口を作る |
| なぜ変えたか・何を確認したか | `decisions-*` は判断の経緯、`verification-*` は日時と環境を限定した実測 | 過去の証拠を現況に読み替えず、後継の正本へリンクする |

## 2. 状態と時点を混同しない

既存の `status`・`last-verified`・`related-code` を使用する。新しい状態項目は、具体的な不足が判明するまでは増やさない。`status` 一つで合意・実装・デプロイの全段階を表したことにはしない。

| 例 | 読み方 | 現行扱いする条件 |
| --- | --- | --- |
| 製品意図のドラフト | 合意済みの前提と将来仮説が同居 | 合意範囲を確認してから仕様化する |
| `status: production` だが乖離警告のある Phase 2 仕様 | フォルダ名・frontmatter だけでは正本と断定できない | 全面再検証と双方の事前確認後に現行仕様として扱う |
| `status: legacy` の旧デプロイ構成 | 過去の構成を記録する資料 | 現行の手順には使わず、後継手順の確定を待つ |
| 決定・検証記録 | その判断日・確認日時の証拠 | 有効性は後続の明示的な合意で決まる。コード・IaC・AWS は反映状態の証拠であり、決定との差があれば逸脱として扱う |

文書には必要に応じて「合意済み／未決」「コード反映済み／デプロイ待ち／環境確認済み」「対象環境と確認日時」を本文で明示する。PR マージを AWS 反映済みと書かない。全面検証でない場合は frontmatter の `last-verified` を進めず、[AGENTS.md](../AGENTS.md) のセクション単位の検証マーカーを使う。

## 3. 旧文書の保管

`docs/archive/` は後継正本が確定し、現在の入口から利用しないことを双方が確認した文書だけを置く。古い日付の決定・検証記録や、現行の内容を含む未整備文書を一括で仮置きしない。

1. 後継正本と影響するリンクを列挙し、文書単位で「全面更新」か「保管」かを決める。
2. 移動する場合は `git mv` で履歴を残し、相対リンク・索引・旧文書冒頭の後継案内を同じ PR で直す。後継未確定なら移動を保留する。
3. `status: production` 文書の更新・状態変更は、理由、影響範囲、コード変更の有無を示し、[AGENTS.md](../AGENTS.md) に従いユーザーの事前確認を得る。

今回の共同確認 PR では文書の移動や個別の production 文書の改稿は行わない。Phase 2 機能仕様は全面更新の候補、旧デプロイ構成は後継確定後の保管候補であって、どちらも本 PR で状態を確定しない。

## 4. 仕様駆動で更新する

作業開始時に目的・業務境界・現行契約の正本を確認し、変更する仕様と受け入れ条件を実装前に記す。合意が必要な製品方針・業務対象は二人で PR 確認する。実装 PR では対応する仕様・テスト・コードを揃え、文書だけ先行したまま「実装済み」にしない。共同確認用 Markdown と実装・デプロイ PR の分離方法は [AI 駆動開発の運用](ops-ai-driven-dev.md) に従う。

AWS 実環境に依存する記述は、許可された対象アカウント・リージョン・環境を特定し、エージェントが読み取り専用 CLI で確認する。確認日時、対象、確認方法、コード・IaC との差、未確認項目を記録する。アクセスできない場合は「未確認」とし、実測したかのように書かない。CLI の観測結果を業務判断の代わりにせず、秘匿値は文書へ転記しない。

## 5. 導入順と今回の合意範囲

1. 本書と `AGENTS.md` で、文書の入口、正本、仕様駆動の更新時点、保管条件を共同確認する。
2. 目的別索引と既存索引の誤誘導を直す。個別文書は適用状態と後継を調べ、全面更新か保管かを決める。
3. 現行文書はコード・実環境と全セクションを照合して更新する。保管が確定した文書だけ `docs/archive/` へ移す。

本 PR で合意したいことは、**浅いディレクトリ＋目的別索引＋現行正本の明示**を採用し、実装に先立つ仕様・受け入れ条件の更新を日常運用にすること。索引全体の改訂、production 文書の内容確認、AWS 実環境の再検証、旧文書の移動は後続の対象別作業とする。
