# Ele-Knowledge 質問箱 Forms設計案

2026年10月20日作成／開発側確認用・未公開

## 1．目的と窓口の使い分け

キーマン・利用者から開発側への質問を受け付け、個別に回答するとともに、共通する内容をFAQに蓄積する。以下は運用の提案であり、Formsの作成・公開はまだ行っていない。

| 内容 | 利用する窓口 |
| --- | --- |
| AIの回答で解決したか、資料が見つかったか、回答が違っていたか | 既存の「解けた／解けない」と理由・補足 |
| 画面や機能をこう変えてほしい | 既存の「こうなってほしい」 |
| 使い方、登録資料、資料追加の相談、キーマン活動などへの質問 | 今回のForms質問箱（案） |
| 回答精度・利用効果の定量評価、会議方針への投票 | 別途案内する評価・賛否確認アンケート |
| 急ぎの障害・利用できない状況 | 既存サポートへ直接連絡。質問箱の確認を待たない |

窓口を迷った場合も受け付け、開発側で適切な担当・窓口につなぐ。回答評価や改善要望を質問箱へ再入力することは求めない。

## 2．Formsへ転記する案内文

フォーム名：Ele-Knowledge 質問箱

Ele-Knowledgeの使い方、登録資料、資料追加、キーマン活動などについて、開発側に確認したいことをお寄せください。初歩的な質問でも構いません。原則として1件の質問につき1回送信してください。

いただいた質問は開発側で確認し、ご本人へ回答します。使い方など、利用者に共通する内容は、個人や現場が特定されない形に整理してFAQへ掲載する場合があります。キーマン活動・会議運営に関する質問は個別に受け付けて回答し、利用者向けFAQには掲載しません。質問本文をそのまま全利用者に公開することはありません。

回答の「解けた／解けない」や改善要望は、システム内のフィードバック機能もご利用ください。急ぎの障害・利用できない状況は、利用者マニュアル記載のサポートへ直接ご連絡ください。

パスワード・確認コード、顧客名や現場名など業務上不要な個人情報・機密情報、PDFを開いたタブのURLは記載しないでください。資料は原則として資料名・版・ページ番号でお知らせください。

※公開時には、返信担当・返信方法と、回答情報の閲覧範囲・保管期間を確定し、この案内にも反映する。

## 3．設問案

氏名・返信先は把握できる方式を基本案とする。組織アカウントから記録できる場合は、同じ情報を設問で重ねて収集しない。匿名受付は今回の基本案には含めず、必要性を別途検討する。

| No. | 設問・入力案内 | 形式 | 必須・任意 |
| --- | --- | --- | --- |
| 1 | お名前／返信先の会社メールアドレス | 短文。アカウント記録ができない場合のみ2設問で設ける | 必須 |
| 2 | 所属部署を教えてください | 短文 | 必須 |
| 3 | 質問の分類を選んでください：使い方・操作／利用開始・アカウント／登録資料・検索対象／資料追加・更新の相談／キーマン活動・打ち合わせ／その他・分類が分からない | 単一選択 | 必須 |
| 4 | 確認したいことを記入してください | 長文。何を知りたいかを記入 | 必須 |

資料や画面画像の添付欄は初期案では設けない。必要な場合は開発側から個別に提出方法を案内する。

設問4の入力例：

「各課で使っている業務資料を追加したいです。登録を相談する際、資料名と版のほかに何を整理すればよいですか。」



送信完了メッセージ案：

「ご質問ありがとうございます。開発側で内容を確認し、ご連絡します。追加の確認をお願いする場合があります。急ぎの障害・利用できない状況は、利用者マニュアル記載のサポートへ直接ご連絡ください。」

## 4．受付・回答・FAQ更新の運用案（開発側用）

| 手順 | 対応内容 |
| --- | --- |
| 受付 | 回答一覧の閲覧を担当者に限定し、受付番号・受付日・分類を付ける |
| 確認 | 既存FAQ・マニュアルを確認。不足情報があれば本人に確認する |
| 回答案の作成 | 開発側で回答し、資料の所管判断などは該当担当へ確認する。未確認の仕様や日程は断定しない |
| 個別回答 | 登録された会社メール等、公開前に定めた方法で本人へ連絡する |
| FAQ化 | 使い方など利用者に共通する質問を一般化し、個人・現場を特定する情報を除く。掲載配慮の希望を確認し、確認済みの回答だけ公開する。キーマン活動・会議運営の質問は個別回答とし、FAQ化しない |
| 更新 | FAQ番号、根拠、確認日、確認者を記録し、仕様変更時に見直す |

管理項目案：受付番号／受付日／質問分類／質問要旨／返信先／担当／状態／回答内容／回答日／FAQ掲載可否／FAQ番号／回答の根拠・確認日。

状態案：受付済み／確認中／追加情報待ち／回答済み／FAQ反映済み。個別回答のみで完了する質問もある。

公開用FAQには、氏名・メールアドレスや個別の質問原文を載せない。問い合わせ原票と公開FAQは別に管理する。

## 5．公開前に決めること

| 項目 | 確認する内容 |
| --- | --- |
| 受付対象・本人情報 | 組織内の対象者、記名方式、氏名・会社メールの取得方法 |
| 担当・確認頻度 | 開発側の主担当・代替担当、回答一覧を確認する頻度 |
| 回答方法 | メールまたはTeams等。一次連絡の目安を設けるか。未設定の期限を利用者に約束しない |
| 情報管理 | 回答一覧の閲覧権限、利用目的、保管期間、削除担当 |
| FAQの公開 | 確認者、掲載場所、更新担当、利用者への周知方法 |

## 6．打ち合わせ方針の賛否確認について

質問箱は随時投稿できる窓口とし、会議方針の投票は対象者・締切を定めた別アンケートで行う案とする。

設問案：「全体への説明が必要な場合を除き、キーマン全員を集めた会議は開催せず、工事区分ごとに開催する方針に賛成ですか。」選択肢：賛成／反対。理由・条件の自由記述欄を任意で設ける。

会議で共有した決定条件は「過半数の賛成」。配布前に、分母を対象者全員とするか有効回答者とするか、回答期限、重複回答の扱い、結果の周知担当を明確にする。条件確定前に採否を判定しない。
