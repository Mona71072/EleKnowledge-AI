# AI 駆動開発の運用（mona ↔ itai 共同）

> **状態:** ドラフト（共同確認用）  
> **目的:** コードとドキュメントがズレないように、双方の AI／人間が同じ手順で進める  
> **きっかけ:** 2026-07-29 の整合確認で、同期ルールが無かったために docs 先行・実装ギャップが残った  
> **関連:** `.cursor/rules/ai-collaboration.mdc` / `.cursor/rules/docs-code-sync.mdc` / `.cursor/skills/joint-pr-review/SKILL.md`

最終更新: 2026-07-29

---

## 1. 合意したいこと（Approve の核）

1. **挙動・API・運用を変えたら、同じ作業単位で正本ドキュメントも更新する**
2. **「実装済」はリポジトリ上のコードと突合できるときだけ使う**
3. **正本以外の古い資料は正にしない**（WARNING＋正本への誘導）
4. **意図・運用ルールだけの変更は、機能／デプロイ PR と混ぜない**（共同確認専用 PR）
5. mona / itai どちらが触っても、上記を守る（相手側エージェントもこの文書と Cursor rules を読む）

---

## 2. なぜ必要か

このリポジトリは AI がコードも docs も書く。  
ルールに「コードと docs を一致させよ」が無いと、次が起きやすい。

| 起きること | 結果 |
|---|---|
| 実装だけ進む | 設計・API が嘘になる。次の会話が誤った前提で提案する |
| docs だけ「実装済」 | デプロイ／評価／共同確認が空振りする |
| 古い機能仕様を正本扱い | 廃止済みキーや旧フローを再提案する |
| 評価の「後続」を出荷表に混在 | 緑信号の誤読 |

コードの正しさだけでなく、**次の AI ターンが読んでも誤らない状態**を成果物とする。

---

## 3. 正本マップ

| 種類 | 正本 | メモ |
|---|---|---|
| API 契約 | `docs/api/*.md` | フロント／Lambda 変更時に必ず見る |
| なぜ変えたか | `docs/impl-log-*.md` | 変更理由の追跡。設計案の代替ではない |
| 合意・微妙な前提 | `docs/decisions-*.md` | 繰り返し防止。必要なら `.cursor/rules` に短く転記 |
| 毎回の AI 動作 | `.cursor/rules/*.mdc` | alwaysApply は少なく・具体的に |
| 繰り返し手順 | `.cursor/skills/**/SKILL.md` | 共同確認は `joint-pr-review` |
| 製品意図 | `docs/PRODUCT_INTENT.md` | ドラフト。ここだけ見てアプリを一気に実装しない |
| 評価の手順 | `docs/eval-*.md` | コマンド・指標の使い方 |
| 評価の落とし穴 | 対応する `docs/decisions-*-eval*.md` | **手順より優先**（楽観を正す側） |
| RAG 検索の前提 | `.cursor/rules/rag-search-principles.mdc` | 番号検索化禁止など |

### 正本にしないもの（読むときは注意）

- `docs/features/production/phase2-rag-chat.md` など、冒頭 WARNING 付きの古い切り出し
- `docs/data-model.md` のうち未更新セクション（更新するまで API／コードを正とする）
- 会話だけの口頭合意（必ず decisions / rules / 本メモへ残す）

古い資料を残す場合の最低条件:

```text
> WARNING: 現行実装と乖離しうる。正本は docs/api/... と ...
```

## 4. 作業単位でのチェックリスト（エージェント必須）

機能・挙動・API・評価・運用のいずれかを変えるとき、完了前に確認する。

- [ ] 変更した挙動に対応する **正本**（上表）を更新した
- [ ] 「実装済 / 未実装 / 後続」の表記がコードと一致する
- [ ] 出荷判断・受け入れ条件に、未実装の指標を“使える前提”で書いていない
- [ ] 設計メモ（`design-*`）と実装がズレる場合、コード修正 **または** design 状態／decisions・impl-log へのギャップ記載をした
- [ ] 意図・運用だけの変更なら、機能実装 PR とブランチ／PR を分けた
- [ ] 根本変更なら `joint-pr-review` に従い相手へ PR で飛ばす

例外（docs 更新を省略してよいもの）:

- タイポ・コメントのみ・挙動不変のリファクタ
- 生成物・gitignore 対象のみ（ただし運用 docs が「出力する」と書いていればその記述は正本のまま）

---

## 5. 表記ルール（ズレ防止）

| 書いてよい | 条件 |
|---|---|
| **実装済** | 当該ブランチ／PR のコードで再現できる。未 push なら「作業ツリー／この PR で実装」と明示 |
| **方針合意のみ / 未実装** | 設計や評価の第2層など。出荷表に混ぜない |
| **後続** | 集計・CI・インフラ待ち。手順 docs に「後続」と書き、主指標表と矛盾させない |
| **ドラフト** | 共同確認前・未 Approve。確定と書かない |

設計（`design-*`）と実装ログ（`impl-log-*`）の役割:

- **design** = 狙いと受け入れ（状態を更新する）
- **impl-log** = 何をなぜ入れたか（コード追従の日記）
- 受け入れチェックボックスは「コード済」と「本番／手動検証済」を混同しない

## 6. mona / itai それぞれの進め方

### 共通（双方のエージェント）

1. 変更前: 意図の言い直し → 変更案 → 合意（`ai-collaboration`）
2. 実装と正本 docs を**同じコミット系列**で出す（意図・運用 PR なら docs + rules のみ）
3. 完了前に §4 チェックリスト
4. 根本変更は PR で相手に見せる（ローカル完結にしない）

### mona → itai

- push / `gh` は `Mona-mebs`（`.cursor/rules/github-account.mdc`）
- 意図・運用専用 PR は base `develop`、先頭で `@yukiworkspace` メンション
- テンプレ: `.cursor/skills/joint-pr-review/SKILL.md`

### itai → mona

- 同じ正本マップ・同じチェックリストで進める
- 根本変更は mona がレビューできる PR にする（本メモと rules を逸脱した「コンソールだけ修正」はしない）
- Lambda 直編集など、リポジトリ外の恒久変更は禁止（ドリフト＝docs/コード不一致の温床）

## 7. 共同確認 PR で見るポイント（本運用）

意図・運用 PR のレビュー観点例:

| ファイル | 見るポイント |
|---|---|
| `docs/ops-ai-driven-dev.md` | 正本マップとチェックリストが実務で使えるか |
| `.cursor/rules/docs-code-sync.mdc` | AI が毎回守れる短さ・具体性か |
| `.cursor/rules/ai-collaboration.mdc` | 本運用への参照が切れないか |

**この変更で決まること（共同確認）:** コード↔docs 同期を双方の標準運用にすること。既存 open PR への相乗り条件。  
**決まらないこと:** 本番 KB の頁メタ確認・第2層 Bedrock Evaluations・ゴールデンの本格ラベリング（別作業）

---

## 8. やらないこと

- 「あとで docs を揃える」を常態化する
- 古い `features/production/*` を仕様の正として実装する
- 口頭だけで正本マップを変える（必ず本メモか decisions を更新）
- （原則）運用ルール**だけ**の変更を、無関係なセキュリティ／UI PR に相乗りさせる

### PR の分け方（原則と相乗り）

| 状況 | 方針 |
|---|---|
| 意図・運用ルールだけの変更 | **別 PR**（共同確認専用）が原則 |
| 既に open な `mona`→`develop` PR が同一デリバリ（同じ RAG/PDCA など） | **相乗り可**。本文に共同確認＋デプロイの両方を書く |
| ユーザーが「既存 PR と一緒に」と明示 | **相乗り**し、新規の薄い PR を無理に切らない |

詳細: `.cursor/rules/working-branch.mdc` / `.cursor/skills/joint-pr-review/SKILL.md`
