# AI 駆動開発の運用（mona ↔ itai 共同）

> **状態:** ドラフト（共同確認用）  
> **目的:** コードとドキュメントがズレないように、双方の AI／人間が同じ手順で進める  
> **きっかけ:** 2026-07-29 の整合確認で、同期ルールが無かったために docs 先行・実装ギャップが残った  
> **関連:** `.cursor/rules/ai-collaboration.mdc` / `.cursor/rules/docs-code-sync.mdc` / `.cursor/skills/joint-pr-review/SKILL.md`

最終更新: 2026-07-29

---

## 1. 合意したいこと（Approve の核）

1. **挙動・API・運用を変えたら、同じ作業単位で正本ドキュメントも更新する**
2. **「実装済」はリポジトリ上のコードと突合できるときだけ使う**
3. **正本以外の古い資料は正にしない**（WARNING＋正本への誘導）
4. **共同確認 PR とデプロイ PR は分ける**（混ぜない）
5. **共同確認同士**なら、既存の意図・運用 PR に相乗りしてよい
6. mona / itai どちらが触っても、上記を守る

---

## 2. なぜ必要か

このリポジトリは AI がコードも docs も書く。  
ルールに「コードと docs を一致させよ」が無いと、次が起きやすい。

| 起きること | 結果 |
|---|---|
| 実装だけ進む | 設計・API が嘘になる。次の会話が誤った前提で提案する |
| docs だけ「実装済」 | デプロイ／評価／共同確認が空振りする |
| 古い機能仕様を正本扱い | 廃止済みキーや旧フローを再提案する |
| 共同確認とデプロイを同一 PR に混在 | レビュー観点が混ざり、Approve 条件が不明になる |

コードの正しさだけでなく、**次の AI ターンが読んでも誤らない状態**を成果物とする。

## 3. 正本マップ

| 種類 | 正本 | メモ |
|---|---|---|
| API 契約 | `docs/api/*.md` | フロント／Lambda 変更時に必ず見る |
| なぜ変えたか | `docs/impl-log-*.md` | 変更理由の追跡。設計案の代替ではない |
| 合意・微妙な前提 | `docs/decisions-*.md` | 繰り返し防止。必要なら `.cursor/rules` に短く転記 |
| 毎回の AI 動作 | `.cursor/rules/*.mdc` | alwaysApply は少なく・具体的に |
| 繰り返し手順 | `.cursor/skills/**/SKILL.md` | 共同確認は `joint-pr-review` |
| 製品意図 | `docs/PRODUCT_INTENT.md` | ドラフト。ここだけ見てアプリを一気に実装しない |
| 評価の手順 | `docs/eval-*.md` | コマンド・指標の使い方 |
| 評価の落とし穴 | 対応する `docs/decisions-*-eval*.md` | **手順より優先**（楽観を正す側） |

### 正本にしないもの

- `docs/features/production/phase2-rag-chat.md` など、冒頭 WARNING 付きの古い切り出し
- 未更新の `data-model.md` セクション（更新するまで API／コードを正とする）
- 会話だけの口頭合意（必ず decisions / rules / 本メモへ残す）

## 4. 作業単位でのチェックリスト（エージェント必須）

- [ ] 変更した挙動に対応する **正本** を更新した
- [ ] 「実装済 / 未実装 / 後続」の表記がコードと一致する
- [ ] 出荷判断・受け入れ条件に、未実装の指標を“使える前提”で書いていない
- [ ] 設計と実装のズレを放置していない
- [ ] **共同確認内容ならデプロイ PR に載せていない**（逆も同様）
- [ ] 共同確認で、既存の意図・運用 open PR に相乗りできるなら相乗りを検討した

例外（docs 更新を省略してよい）: タイポ・挙動不変のリファクタのみ。

---

## 5. 表記ルール

| 書いてよい | 条件 |
|---|---|
| **実装済** | 当該ブランチ／PR のコードで再現できる。未 push なら明示 |
| **方針合意のみ / 未実装** | 出荷表に混ぜない |
| **後続** | 主指標表と矛盾させない |
| **ドラフト** | 共同確認前。確定と書かない |

---

## 6. PR の分け方（必須）

| 種類 | 載せるもの | 相乗り |
|---|---|---|
| **デプロイ PR** | アプリ実装・SAM・API 契約の実装追従 | 他のデプロイ系と必要なら。**共同確認を載せない** |
| **共同確認 PR** | `PRODUCT_INTENT`・`.cursor/rules`・skills・運用メモ | **既存の共同確認 PR 同士**なら相乗り可 |

相乗りしてよい例:

- 既に open な意図・運用 PR（例: #28）があり、今回も AI 駆動／ルールの話
- ユーザーが「前の共同確認と一緒に」と明示した

相乗りしてはいけない例:

- デプロイ用 PR（#33 など）に運用ルールだけを足す
- セキュリティ修正 PR に PRODUCT_INTENT を混ぜる

---

## 6b. PR のわかりやすさ（合格線）— テンプレ埋めだけでは不十分

レビュアーが **冒頭30秒** で次を答えられること。できないなら送らない／書き直す。

| 問 | 本文に必須 |
|---|---|
| 何の PR？ | 共同確認 **または** デプロイ（どちらか一方）。タイトルも中身と一致 |
| 何をすればいい？ | Approve なら Yes/No 質問。デプロイなら実行コマンドと確認項目 |
| どこを読む？ | 読む順（正本を先に）。ファイルが多いほど必須 |
| 範囲は？ | 決まること／決まらないこと、または核／付随／範囲外 |

**禁止:** パス羅列だけのサマリ、「一式」「など」で核をぼかす、テンプレコピペだけで今回差分に触れない。

短則: `.cursor/rules/pr-clarity.mdc`

## 7. mona / itai

### 共通

1. 変更前: 意図の言い直し → 変更案 → 合意
2. 共同確認とデプロイが両方必要なら **PR を 2 本**
3. 完了前に §4 チェックリスト
4. PR 送付前に §6b / `pr-clarity.mdc` を満たす

### mona → itai

- push / `gh` は `Mona-mebs`
- 共同確認は先頭で `@yukiworkspace`、テンプレは `joint-pr-review`

### itai → mona

- 同じ正本マップ・同じチェックリスト
- 根本変更は mona がレビューできる共同確認 PR にする

## 8. この PR で決まること / 決まらないこと

**決まる:**

- コード↔docs 同期を双方の標準運用にすること
- 共同確認とデプロイを分けること
- 共同確認同士の相乗り条件
- PR 本文のわかりやすさ合格線（テンプレ埋めだけでは不十分）

**決まらない（別 PR）:**

- 個別機能のデプロイ（RAG 追記結合などはデプロイ PR）
- 本番 KB 検証・第2層評価・ゴールデン本格ラベリング
- 既存の巨大デプロイ PR の分割そのもの（必要なら別途提案）
