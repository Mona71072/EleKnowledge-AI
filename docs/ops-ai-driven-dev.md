# AI 駆動開発の運用（mona ↔ itai 共同）

> **状態:** ドラフト（共同確認用）  
> **目的:** コードとドキュメントがズレないように、双方の AI／人間が同じ手順で進める  
> **きっかけ:** 2026-07-29 の整合確認で、同期ルールが無かったために docs 先行・実装ギャップが残った  
> **関連:** `.cursor/rules/ai-collaboration.mdc` / `.cursor/rules/docs-code-sync.mdc` / `.cursor/skills/joint-pr-review/SKILL.md`

最終更新: 2026-09-10

---

## 1. 合意したいこと（Approve の核）

1. **挙動・API・運用を変えたら、同じ作業単位で正本ドキュメントも更新する**
2. **「実装済」はリポジトリ上のコードと突合できるときだけ使う**
3. **正本以外の古い資料は正にしない**（WARNING＋正本への誘導）
4. **共同確認 PR とデプロイ PR は分ける**（混ぜない）
5. **共同確認同士**なら、既存の意図・運用 PR に相乗りしてよい
6. **業務対象を追加／除外する変更は、根拠・決定者・対象外データの扱い・見直し条件を記録する**
7. **誰が `develop` へマージするか・いつマージしてよいかを PR 本文に書く**（Approve とマージ担当を混ぜない）
8. mona / itai どちらが触っても、上記を守る

---

## 2. なぜ必要か

このリポジトリは AI がコードも docs も書く。  
ルールに「コードと docs を一致させよ」が無いと、次が起きやすい。

| 起きること | 結果 |
|---|---|
| 実装だけ進む | 設計・API が嘘になる。次の会話が誤った前提で提案する |
| docs だけ「実装済」 | デプロイ／評価／共同確認が空振りする |
| 古い機能仕様を正本扱い | 廃止済みキーや旧フローを再提案する |
| 共同確認とデプロイを同一 PR に混在 | レビュー観点が混ざり、Approve 条件が不明になる |

コードの正しさだけでなく、**次の AI ターンが読んでも誤らない状態**を成果物とする。

## 3. 正本マップ

| 種類 | 正本 | メモ |
|---|---|---|
| API 契約 | `docs/api/*.md` | フロント／Lambda 変更時に必ず見る |
| なぜ変えたか | `docs/impl-log-*.md` | 変更理由の追跡。設計案の代替ではない |
| 合意・微妙な前提 | `docs/decisions-*.md` | 繰り返し防止。必要なら `.cursor/rules` に短く転記 |
| 毎回の AI 動作 | `.cursor/rules/*.mdc` | alwaysApply は少なく・具体的に |
| 繰り返し手順 | `.cursor/skills/**/SKILL.md` | 共同確認は `joint-pr-review` |
| 製品意図 | `docs/PRODUCT_INTENT.md` | ドラフト。ここだけ見てアプリを一気に実装しない |
| 評価の手順 | `docs/eval-*.md` | コマンド・指標の使い方 |
| 評価の落とし穴 | 対応する `docs/decisions-*-eval*.md` | **手順より優先**（楽観を正す側） |

### 正本にしないもの

- `docs/features/production/phase2-rag-chat.md` など、冒頭 WARNING 付きの古い切り出し
- 未更新の `data-model.md` セクション（更新するまで API／コードを正とする）
- 会話だけの口頭合意（必ず decisions / rules / 本メモへ残す）

## 4. 作業単位でのチェックリスト（エージェント必須）

- [ ] 変更した挙動に対応する **正本** を更新した
- [ ] 「実装済 / 未実装 / 後続」の表記がコードと一致する
- [ ] 出荷判断・受け入れ条件に、未実装の指標を“使える前提”で書いていない
- [ ] 設計と実装のズレを放置していない
- [ ] **共同確認内容ならデプロイ PR に載せていない**（逆も同様）
- [ ] 共同確認で、既存の意図・運用 open PR に相乗りできるなら相乗りを検討した
- [ ] 業務対象の追加／除外がある場合、`docs/decisions-*.md` 等に選定根拠・決定者・影響件数・対象外データの扱い・見直し条件を記録した

例外（docs 更新を省略してよい）: タイポ・挙動不変のリファクタのみ。

## 6. PR の分け方（必須）／同種はまとめる

| 種類 | 載せるもの | まとめ方 |
|---|---|---|
| **デプロイ PR** | アプリ実装・SAM・API 契約の実装追従 | 未マージのデプロイ系で不都合が無ければ **1 本に寄せる**。共同確認は載せない |
| **共同確認 PR** | `PRODUCT_INTENT`・`.cursor/rules`・skills・運用メモ | 未マージの共同確認系で不都合が無ければ **1 本に寄せる**。デプロイは載せない |

### PR を増やしすぎない

open の細かい PR が増えると、レビュー・マージ順・メンションが破綻する。  
**新規 PR の前に「同種の未マージへ載せられるか」を必ず検討する。**

| まとめてよい | 分けた方がよい |
|---|---|
| コンフリクトが実質ない | 共同確認 ↔ デプロイ（種類が違う） |
| レビュー観点・Approve 条件が同じ | 片方だけ先にマージ／デプロイしたい |
| デプロイ手順が同じ／共存可能 | まとめると読む順でもレビュー不能 |
| ユーザーが「一緒に」と明示 | 無関係な大型テーマの同居 |
| | **相手（itai / mona）が判断できない大きさ** |

### デカすぎて相手が判断できないときは分ける（必須）

同種まとめ・増殖禁止より、**レビュー可能性を優先する**。

次のいずれかなら、まとめず **分ける**（または既存巨大 PR から切り出す）:

- 読む順を書いても、相手が「これで Approve／デプロイしてよいか」判断できない
- テーマが複数（例: セキュリティ + RAG + お知らせ + UI）で、1人のレビュー単位を超える
- 「核／付随」を付けても付随が本体より大きい
- ユーザーまたはレビュアーが「大きすぎて判断できない」と言った

分け方の目安: **デプロイ単位 × レビュー観点**（例: 認可／RAG／PDCA／お知らせ）。コミット1つ＝PR1つまでの細分化はしない。

やってはいけない: デプロイに運用ルールだけを足す／共同確認に実装デプロイを混ぜる／不都合が無いのに同種 PR を増やし続ける／**相手が判断できない巨大 PR を「まとめ推奨」で放置する**

### マージ順（順不同が原則）

共同確認 PR とデプロイ PR は **別のことを載せる**前提なので、ファイルが重なっていなければ **どちらを先に `develop` へマージしてもよい（順不同）**。

| 状況 | マージ順 |
|---|---|
| 種別が分かれ、触るファイルが重ならない | **順不同**。「先に共同確認必須」などと書かない |
| 同じファイルを両 PR が変えている | **不具合**。デプロイ側から共同確認ファイルを外す／同種なら1本にまとめる。順番で誤魔化ししない |
| DB 移行→コードなど、実依存がある | その依存だけ本文に「なぜこの順か」を1行で書く |

エージェントが「推奨マージ順: #28 → #33」のように **偽の順番**を書いてはいけない。

### 例外: stacked PR（実依存があるとき）

同じファイルを複数の独立 PR が変えるのは原則 **不具合**。ただし次を **すべて**満たすなら stacked（後続の base = 先行の head）を許容する。

- 後続が先行の上にしか載せられない実依存がある（例: 同じ `app.py` の機種フィルタを、カテゴリ常時フィルタの上に積む）
- PR 本文に **なぜ積むか** と **先行を先に `develop` へ入れること** を1行で書く
- 先行がマージされたら、後続の base が `develop` に付く想定を本文に書く

**base 付け替え:** 先行マージ後に後続がコンフリクトしたら、順番で誤魔化さず **先行側の最終形に合わせる**。独立 PR に「推奨マージ順」を並べるのは stacked の代替にしない。

### マージ担当（誰が・いつ押すか）— 必須

Approve（内容OK）と **マージボタンを誰が押すか** は別である。
書かないと open PR が溜まる。PR 本文に次を必ず書く。

| 種類 | 内容を見る人 | **`develop` へマージする人** | いつ |
|---|---|---|---|
| **デプロイ**（実装・SAM・フロント） | mona（レビュー） | **itai（@yukiworkspace）** | mona が「**マージ可**」と書いたら、原則 **その日〜翌日** |
| **共同確認**（意図・rules・運用メモ） | 相手（Yes/No） | **PR を出した側** | 相手の Approve（または明示の Yes）から原則 **48時間以内** |
| **記録のみ**（検証メモ等・デプロイ不要） | mona（誤り指摘） | **itai**（ブロッカーが無ければ） | mona がブロッカーなしと言ったら **その日〜翌日** |
| **置き換え済み** | — | **マージしない。出した側が Close** | 後継が本線になった時点 |

**コメントの書き分け（必須）:**

| 言い方 | 意味 |
|---|---|
| 内容OK / Approve | 中身は認める。**まだマージしてよいとは限らない**（依存・順番待ちがあり得る） |
| **マージ可** | 条件を満たした。**マージ担当がボタンを押してよい** |
| マージ可（条件: …） | 条件付き。条件を満たしてからマージ担当が押す |

レビューコメントや PR 本文の例:

```markdown
## マージ
- **担当:** itai（デプロイ） / mona（共同確認・自分が出した側）など
- **マージ可の条件:** （例: #57 マージ後 / フロントの文言修正後 / なし）
```

**禁止:**

- Approve したのにマージ担当・期限を書かない
- 「内容OK」だけ書いて、相手がマージしてよいか分からない状態を残す
- 作業ブランチや個人確認用ブランチへの反映を、本家 `develop` マージ済みと読める書き方をする
- 置き換え済み PR を Close せず open のまま残す

短則: `.cursor/rules/working-branch.mdc` / `.cursor/rules/pr-clarity.mdc`

## 6b. PR のわかりやすさ（合格線）— テンプレ埋めだけでは不十分

レビュアーが **冒頭30秒** で次を答えられること。できないなら送らない／書き直す。

| 問 | 本文に必須 |
|---|---|
| 何の PR？ | 共同確認 **または** デプロイ（どちらか一方）。タイトルも中身と一致 |
| 何をすればいい？ | Approve なら Yes/No 質問。デプロイなら実行コマンドと確認項目 |
| **誰がマージする？** | **マージ担当**（itai / 出した側 等）と、**マージ可の条件**（なければ「なし」） |
| どこを読む？ | 読む順（正本を先に）。ファイルが多いほど必須 |
| 範囲は？ | 決まること／決まらないこと、または核／付随／範囲外 |

**禁止:** パス羅列だけのサマリ、「一式」「など」で核をぼかす、テンプレコピペだけで今回差分に触れない。

短則: `.cursor/rules/pr-clarity.mdc`

## 6c. なぜ会話が壊れるか（2026-09-10）

詳細: `docs/decisions-2026-09-10-pr-conversation.md`（#103 で正本を `AGENTS.md` へ移した）

**直す前**に起きていたずれ（#103 後の現行ルールではない）:

- Claude Code は `CLAUDE.md` → `AGENTS.md` を読む。当時、会話ルールは Cursor の `pr-clarity` / `joint-pr-review` にしか無かった
- 当時の `AGENTS.md` は「細かく分ける」、Cursor 側は「同種はまとめる」で食い違っていた（現行は「相手が判断できる単位。同種は寄せる」）
- `CLAUDE.md` に古い docs 一覧や「PR は細かめ」があると、Claude Code だけが古い運用に従う（現行の `CLAUDE.md` はポインタのみ）
- マージ担当欄だけ埋めて Yes/No を書かないと、相手は何を認めればよいか分からない
- 進行中の相手 PR 本文をテンプレ是正で書き直すと、レビューが壊れる
- スキル／テンプレの「マージ可の条件」に Approve だけを書くと、直したあとも同じ本文が量産される

直す場所は **`AGENTS.md` の「PR の会話」**。Cursor 短則やスキルのテンプレだけ直しても、正本と食い違えば再発する。

## 7. mona / itai

### 共通

1. 変更前: 意図の言い直し → 変更案 → 合意
2. 共同確認とデプロイが両方必要なら **PR を 2 本**
3. 完了前に §4 チェックリスト
4. PR 送付前に §6b / `pr-clarity.mdc` を満たす

### mona → itai

- 個人・端末固有の GitHub 認証、フォーク、リモート運用は各自の未追跡ローカル設定で管理する
- 共有ルールにはアカウント名や認証切替手順を置かず、他の参加者へ個人設定を適用しない
- push / PR は明示された依頼範囲内で行い、操作前に各自が認証主体と対象リポジトリを確認する
- 共同確認は先頭で `@yukiworkspace`、テンプレは `joint-pr-review`

### itai → mona

- 同じ正本マップ・同じチェックリスト
- 根本変更は mona がレビューできる共同確認 PR にする
- 自分宛てメンションは不要。mona が Yes/No できる本文にする
- mona の個人・端末固有設定を itai や itai 側エージェントへ適用しない

## 8. この PR で決まること / 決まらないこと

**決まる:**

- コード↔docs 同期を双方の標準運用にすること
- 共同確認とデプロイを分けること
- 同種の未マージ PR は不都合が無ければまとめる（PR 増殖禁止）
- **相手が判断できない巨大 PR は分ける**（まとめ推奨で放置しない）
- 共同確認とデプロイはファイルも分け、**マージは順不同**（偽の順番依存を作らない）
- **マージ担当と「マージ可」条件を PR 本文に書く**（Approve とマージ担当を混ぜない）
- PR 本文のわかりやすさ合格線（テンプレ埋めだけでは不十分）
- 業務対象の追加／除外は、決定記録と共同確認が終わるまでマージしない

**決まらない（別 PR）:**

- 個別機能のデプロイ（RAG 追記結合などはデプロイ PR）
- 本番 KB 検証・第2層評価・ゴールデン本格ラベリング
