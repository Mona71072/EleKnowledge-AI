## 結論（先に）

第1層（機械採点）自体は **方向として正しい**（成功条件＝**該当資料への到達**、LLM 不要、アプリ実経路を通せる）。頁は副次。  
ただし **「回した＝改善した」ではない**。次を守らないと誤った緑信号になる。

1. **主指標は `hit_in_candidates`（ラベル済みのみ）**。`gate_accuracy` 単独で出荷判断しない  
2. **ラベル済みが N&lt;10 のときは「採点」ではなく「ラベリング作業」扱い**（率は参考にしない）  
3. **`page_hit` は副指標**（あれば見る。成功必須ではない。頁を主指標に戻さない）  
4. **難問枠（drawing / incident / qsheet）を分けて見る**。全体平均だけ見ない  
5. **第1層が測らないもの**（Claude の作文・多ターン聞き返し後・prd KB 差分・現場満足）を混同しない  
6. **現場フィードバックとセットで回す**（セット外の失敗は見えない）

## 多視点で見た問題と是正

### A. 製品意図との整合

| リスク | 内容 | 是正 |
|---|---|---|
| 成功条件のすり替わり | `hit@k` や `gate_accuracy` が良くても、UI 上の候補5件に出ていなければ利用者は届かない | **出荷判断の主指標 = `hit_in_candidates`**（ラベル済み分母）＝資料到達 |
| 頁を主成功に戻す | かつて「頁到達」が成功定義だったが **訂正済**（成功＝資料到達＋疑問解決。頁は副次） | `page_hit` は **副指標のまま**。`#page` 必須化や主指標昇格を再提案しない |
| 図書番号への退行 | ラベルが `C-591124` だと「番号検索すれば緑」に寄りやすい | 質問文は **自然文のまま**。番号は正解ラベル側だけ。主導線に番号入力を足さない |

### B. 統計・サンプルの嘘

| リスク | 内容 | 是正 |
|---|---|---|
| 分母が小さい | 現状ほぼ未ラベル。2〜3問で `hit@5=1.0` と出ても無意味 | **ラベル済み N&lt;10 → 率を意思決定に使わない**。ラベリング優先 |
| ゲート問で平均が盛れる | G001/G103 は通しやすい。`gate_accuracy` だけ見て安心しがち | ゲートは **回帰防止用**。検索改善の可否はラベル済みの到達率で判断 |
| 易問だらけ | 本命（C/TI/据付基準）ばかりだと全体平均が良く見える | タグ `hard` / `drawing` / `incident` / `qsheet` を **分けて報告**。難問が悪化していないか必須確認 |
| セット過学習 | 同じ10問だけを緑にするチューニング | 週次で chatlogs 由来の新問を追加。改善確認後も **新規ラベル問で再確認** |

### C. ラベル品質（採点の土台）

| リスク | 内容 | 是正 |
|---|---|---|
| 正解が複数ある | OR 一致（どれか1つ当たれば hit）。妥当だが「本命を取りこぼし別資料で緑」がありうる | `expected_documents` に **本命を先に書く**。必要なら `notes` に「許容資料」を明記 |
| 部分一致の偽陽性 | `doc_matches` は部分文字列。短い断片（`C-59`）は別資料に食らう | ラベルは **図書番号フル**（例: `C-591124`）。短すぎる期待値は禁止 |
| カタログ重複 | 同一 `file_name` 重複グループが多数（survey） | 一致はファイル名ベースでよいが、**版・改訂の取り違え**は人が notes で注意 |
| 誰がラベルするか | 工事知識が要る。開発だけで正解を決めない | フロー: スクリプト上位候補 → mona が候補確定 → **迷ったら現場代理人に「この資料で合ってるか」確認**。確信のないラベルは入れない（空のまま残す） |
| 未ラベル混入 | `labeled=false` は hit 集計から除外される（実装どおり） | 正しい。**空ラベルを無理に埋めない** |

### D. 測定範囲の穴（「同一経路」の限界）

第1層が **通すもの**

- 正規化 → 聞き返し（履歴なし）→ 本命優先 retrieve → 略語展開 → 弱い検索ゲート → 候補資料

第1層が **通さない／測らないもの**（緑でも安心しない）

| 穴 | 影響 | 補完 |
|---|---|---|
| Claude 回答本文 | 正しい資料でも作文が誤断定しうる | 第2層（Faithfulness 等）＋ 👍/👎 |
| 多ターン（clarify 後の追記） | `chat_history=[]` 固定。`compose_search_query` による結合検索は未評価 | 別タグ `multi_turn` を将来追加。当面は人手で1〜2本確認。単体テストで結合ロジックは担保 |
| フロント擬似ストリーム等 | UX は対象外 | 対象外でよい |
| prd KB ≠ dev KB | 資料同期遅れで「dev 緑・prd 赤」 | デプロイ前に **dev/prd の同期状態を確認**。重大変更は prd でもスモーク |
| フィルタなし vs 現場の機種指定 | ゴールデンの `filters` が現場操作と違うと乖離 | 実質問を入れるとき **当時の機種・カテゴリを filters に残す** |

### E. 運用・組織

| リスク | 内容 | 是正 |
|---|---|---|
| Check がローカル依存 | CI なし。回し忘れで壊したまま PR | PR 前のチェックリストに「第1層実行＋前回比」を書く。自動化は後続 |
| Act が遅い | Lambda は itai さん `sam deploy` 待ち | 第1層で悪化なら **PR しない**。改善時だけ依頼。dev 自走は別合意 |
| 現場ループ欠落 | セット外の失敗は永遠に見えない | **Plan の入力はチャットの bad / not_found / 現場メモを正**。セットは倉庫、現場が源流 |
| 個人情報・現場固有 | 実質問を git に入れると工事番号等が混入しうる | 質問文は **一般化**（固有名は伏せる）。必要なら社内のみの別ファイル（gitignore）を検討 |

### F. 変更判断のルール（是正後）

変更を「良い」とみなす条件（すべて満たす）:

1. ラベル済み **N ≥ 10**（それ未満は参考）  
2. **`hit_in_candidates` が悪化していない**（同点以上。可能なら改善）  
3. タグ `hard` 付きの到達が **悪化していない**  
4. `gate_accuracy` が **意図したゲート問で破綻していない**（clarify / not_found の回帰なし）  
5. 可能なら `page_hit` 対象問で悪化なし  

「悪いのに緑に見える」典型:

- ゲート問だけ増えて `gate_accuracy` 上昇  
- 易問だけラベルして全体 hit 上昇  
- 短い `expected_documents` で偽陽性  
- Claude だけ壊して retrieve は緑（第1層の守備範囲外）

## 是正後の運用（やり方）

### 役割

| 誰 | 何をするか |

### 週次サイクル（目安）

```text
月〜: chatlogs / 👎 / not_found から 3〜10 問を golden_set に追加（未ラベル可）
   : run_retrieve_eval.py → 上位候補を見てラベル（迷ったら現場確認）
火〜: しきい値・フィルタ・クエリ処理を変更
   : 再実行 → --compare（主指標・hard 枠を見る）
水〜: 是正ルールを満たせば PR（@yukiworkspace）
節目: 第2層 Bedrock Evaluations（BYOI）
```

### 日常コマンド

```bash
# ラベリング支援〜全問
AWS_PROFILE=<dev用> python3 scripts/eval/run_retrieve_eval.py

# 変更前後
python3 scripts/eval/run_retrieve_eval.py --compare eval-results/retrieve-eval-<前回>.json

# ゲート回帰だけ素早く
python3 scripts/eval/run_retrieve_eval.py --only G001,G103
```

### セット記入の約束

- `query`: 現場の自然文（一般化可）。**番号入力前提の文にしない**  
- `filters`: そのとき選んでいた機種・カテゴリを残す  
- `expected_documents`: 図書番号フル。短すぎ禁止。未確定なら空  
- `expected_pages`: 分かるときだけ（副指標）  
- `expected_gate`: clarify / not_found / pages  
- `tags`: `hard` / `drawing` / `incident` / `qsheet` / `gate` / `本命` など

## Plan の入力源（優先順）— 是正後

1. **管理コンソール「失敗一覧」**（`/admin/failures`）

   - **`unresolved`（疑問が解けない）** は「資料が悪い」決め打ちにしない。候補・snippet・作文・聞き返し・KB欠落を failures で人手振り分け  
   - 「ゴールデン候補をコピー」で `golden_set.jsonl` 1行を取得  
2. 現場メモ／Slack（一覧に無い・口頭の補足）  
3. survey 難問枠の合成問（補助）

### なぜ「チャット理由」と「admin 一覧」の両方か（2026-07-29）

| 片方だけだと足りない | 理由 |
|---|---|
| 一覧だけ（理由なし 👎） | 資料ミス・解決失敗・作文ミスが混ざり、直す場所が分からない |
| 理由付き 👎 だけ | **not_found は自動で付くがクリックされない** → 一覧が無いと収穫できない |
| `unresolved` を KB 欠陥と即断 | 複合信号。failures で振り分けてから手を打つ |
| DynamoDB 手探り | 「ワンクリックで得る」に反する。回らない |

制約（守ること）:

- 理由は **任意ワンタップ**。必須の長文は課さない（フィードバック率が落ちる）
- 一覧は **admin のみ・サーバー側 403**。質問文に工事番号が混じりうる → コピー後に一般化
- Scan はホットウィンドウ向け。規模が伸びたら Athena

合成問だけで緑にしても、現場 PDCA にはならない。
