# 【案】使うほど育つノウハウ基盤：改善ループの自動化

> ステータス: 案（議論用）。実装は含みません。

## 背景と方針

- 昇降機のノウハウは、業務・技術・仕様・ルールと幅が広く、量も多い。
- RAG だけに頼ると、回答の精度にばらつきが出やすい。そのため RAG は主役にしない。
- 代わりに、テーマごとのノウハウを Markdown で見える形にする。
- 現場や熟練者には「ここに書いてある／書いていない」を指摘してもらう。その差分をノウハウとして積み上げる。
- この流れを AI でできるだけ自動化する。

## 1. 知識を種類で分ける

| 種類 | 例 | 置き場所 | 更新の仕方 |
|---|---|---|---|
| 正本がある知識 | 仕様、規格、法令、社内ルール | 原文を参照（コピーしない） | 改訂を追い、版と改訂日を記録 |
| 構造化できる事実 | 型番、数値、改訂日 | DB | データとして更新 |
| 暗黙知 | 判断のコツ、つまずきどころ、現場の注意点 | テーマ別 Markdown | 下のループで育てる |

Markdown で育てるのは暗黙知だけに絞る。正本がある内容は、要約せずに原文へのリンクで示す。

## 2. 基本ループ

KCS（Solve/Evolve）、Karpathy の LLM Wiki、Claude Code のメモリと同じ考え方を取り入れる。

1. AI がテーマ別のノウハウ Markdown と回答を示す。
2. 現場や熟練者が、チャットで「足りない」「違う」と指摘する。
3. AI が指摘を差分にまとめ、追記案（PR や提案）を作る。
4. 熟練者が承認したものだけを正本に入れる。
5. Git の差分で、誰がいつ何を変えたかの履歴が残る。

## 3. 今ある RAG 機能を「検証役」と「材料」として使う

RAG は回答の主役ではなく、ノウハウと資料の質を上げる道具として使う。

- **突き合わせ**: RAG の検索結果や回答と元資料を AI が照合し、次のものを見つける。
  - 内容のずれ
  - 根拠の不足
  - 資料どうしの矛盾
  - 古い記述
- **候補化**: 見つけた結果を、ノウハウ Markdown への追記候補や、元資料の修正候補にまとめる。
- **設定の改善**: 検索や分割（チャンク）の設定について、改善できそうな点を週ごとに出す。
  - 例: 引けなかった質問の傾向、分割の境目で切れた根拠

## 4. AI で自動化する部分

- 日ごとのチャット記録から、次の 3 つを抽出して追記候補を自動で作る。
  - 答えられなかった質問
  - 根拠が薄い回答
  - 繰り返し出てくる修正
- 法令や基準が改訂されたときは、それを引用している確認済みのノウハウを自動で洗い出す。
- 矛盾や古い記述がないかを定期的に点検する。

## 5. 人が必ず入る部分

- 据付や品質など、影響が大きい領域は熟練者の承認を必須にする。
- 自動で反映してよい種類の線引きは要検討。
  - 例: 誤字やリンク切れは自動、手順や判断は承認制

## 6. 小さく始める

- よく聞かれるテーマを数件選び、1 テーマ 1 枚から作る。
- 効果を週ごとに記録する。指標の例は次のとおり。
  - 同じ質問の再質問率
  - 修正の回数
  - 未回答の件数
  - 根拠不足と判定された回答の件数

## 7. 規模が育ったら

- 関係をたどる用途に限って、上にナレッジグラフを足す。
  - 例: 部品、手順、規格のつながり
- 更新が多い知識にはファインチューニングを使わない。

## 未決事項

- 現場の人が回答を「直す」場所を、どの画面にどう用意するか。
- 承認者を誰にするか。承認待ちが滞ったときにどうするか。
- 既存のチャット記録やお知らせ機能と、どうつなぐか。
