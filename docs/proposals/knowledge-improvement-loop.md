# 工技先輩とノウハウ収集の構想: まず管理者へ読取連携を相談する

まずOneNote・Microsoft Listsの読み取り連携に必要な権限を、対象を絞って管理者へ相談したい。既存の記録と技術資料を関連付け、担当者が確認するMarkdownをノウハウ本文として育てる構想を、その相談の背景として共有する。

この文書は共同確認用の提案。権限付与、実データ取得、検索対象の拡大、実装・デプロイ、管理者への連絡はまだ行っていない。

## 最初に確認したいこと

1. itaiさんに、管理者への相談窓口と、最初に対象とするOneNote / Listsの所管・範囲を確認していただけるか。
2. 読取に必要な権限・認証方式に加え、取得物の保存先、AIに入力してよい範囲、整理した知識の共有先を一緒に相談する方針でよいか。
3. OneNoteへの還元は、KBとの照合結果・未確認点を含む追記案を担当者が確認・編集・コピーして手動で追加する範囲でよいか。自動追記や書込権限は求めない。

管理者への相談文のたたき台と確認項目は[構想の§0](../concept-2026-10-19-kougi-senpai-knowledge-cycle.md#0-まず管理者へ読み取り連携を相談する)にまとめた。対象ノートやリスト、読者、モデル入力先は未確定であり、読取権限だけで派生知識の再配布まで許可されたとは扱わない。

## 構想の全体像

1. Listsの不具合・原因・対策、OneNoteの業務上の注意点、既存KBの関連資料を取り込む。
2. AIが関連付け・整理・Markdownの修正差分を提案する。
3. 担当者がWeb画面で原資料・適用条件・差分を確認し、特定版を承認・公開する。Obsidianの編集も同じ知識本文と版管理へ戻す。
4. 工技先輩エージェントが公開済みMarkdownを読み、必要に応じて本人が閲覧できる既存KBの原資料を探す。
5. 利用者が現場の結果・経験者の補足を明示的に送り、担当者が確認してMarkdownを育てる。
6. 周知したい知見はKBと照合して追記の価値・矛盾・未確認点を示し、担当者がOneNoteへ手動で追加できる文章を用意する。

重要な注意点、条件の違い、教育・引継ぎも対象とし、頻出テーマや暗黙知だけに限定しない。正式な仕様・基準は原資料の所管を優先する。KBが生成した回答文を正しさの根拠にせず、該当資料の版と箇所へ戻る。

## 今回の範囲

- 管理者へ読取連携を相談するための目的と確認事項をまとめる。
- 収集・Markdown編集・工技先輩の探索・OneNoteへの手動還元という構想を共有する。
- 読取の相談と、構想全体の採用・実装判断を分ける。
- OneNote / Listsへの自動書込、全会話の無断収集、テナント全体の読取、Microsoft管理者権限の利用者への付与は前提にしない。

元資料・生成済みMarkdownの実物、対象と読者、所管と代替担当、AI入力と保存の許可、Microsoftの認証・同意、既存KBで根拠の版へ到達できるかを確認する。初期は少数テーマで、相談→結果収集→Markdown改訂→次の相談で再利用→OneNoteへの手動追記と訂正追跡までを試す。実測していない効果・費用・工数を確定しない。
