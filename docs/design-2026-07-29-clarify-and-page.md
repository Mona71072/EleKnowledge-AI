## 1. 目的

見当違いの作文を止め、**該当資料に到達して疑問を解決できる**ようにする。

当面の成功:

1. 曖昧な質問には答えないで聞き返す  
2. 機種が分かる状態で本命資料（C / TI / 据付基準）を探す  
3. 候補を **資料名 ＋ 開く** で上に出す（**ページ番号はメタがあれば表示。必須ではない**）  
4. 弱い検索なら作文しない

> **訂正:** 「5分以内に該当 PDF のページまで」は当面の主成功から外した。頁 UX（`#page` 等）も必須化しない。

---

## 2. ユーザー操作（完成イメージ）

### A. 曖昧なとき（聞き返し）

利用者が「振動がする」「騒音」「動かない」「ドアが開かない」などと送る。

→ AI は長文回答せず、例えば:

> 該当資料を探すために教えてください。  
> 1. 機種（または工事番号）※分かれば精度が上がります  
> 2. 何が？（かご／ドア／巻上機／制御盤 など）  
> 3. いつ？（走行中／停止中／開閉時 など）

利用者が追記を返す → そのあと検索。  
※ 機種が最後まで無い場合でも一般資料は候補にしうるが、**特定機種の事実としては断定しない**。

### B. 条件が足りているとき（資料候補）

画面の上から:

1. **資料候補リスト**（最大3〜5件）  
   - 資料名  
   - カテゴリ（C / TI / 据付基準）  
   - ページ（例: p.42）— **あれば**。無ければ「ページ不明」でよい  
   - 関連度（任意）  
   - 「開く」リンク  
2. **短い整理**（任意・短く。断定しない）  
3. 弱いとき: 「条件に合う資料が見つかりません。機種や症状を追加してください」

## 3. 処理フロー（v0）

```
質問受信
  │
  ├─ [1] 不足チェック（ルール中心）
  │     症状系なのに機種なし？
  │     YES → 聞き返し（一般仕様のみの質問は検索へ進んでよい）
  │     直前が聞き返しなら追記を結合して [2] へ
  │
  ├─ [2] 検索（本文 HYBRID。メタは母集団の絞り込みのみ）
  │     カテゴリ未指定（UI）: 内部で本命（C/TI/据付基準）を先に retrieve
  │                           → 弱ければ全資料へ拡大（UI の全検索合意は維持）
  │     カテゴリ指定あり: ユーザー選択を尊重
  │     機種あり: 当該機種 OR 全機種共通（* / general / 空欄）
  │     機種なし: 一般資料も含む（断定は弱める）
  │
  ├─ [3] 弱い？
  │     0件 or スコア低 → 作文せず「見つからない」＋聞き返しヒント
  │
  └─ [4] 応答
        pageCandidates[] を本体に
        content は短文補助（または空でも可）
```

初期は **ルールベースの聞き返し**（LLM分類は後回し）。誤って聞き返す方が、誤って断定するよりマシ。

## 4. 聞き返しルール（v0 案）

### 機種

- **機種なしでも検索してよい**（据付基準など `*` / `general` の一般資料があるため）
- ただし次は **機種を強く促す**（必須ストップではない）:
  - 「振動／騒音／動かない／〜できない」など不具合・症状系
  - 機種固有の仕様・寸法・動作の確認
- 機種があるとき: その機種 **OR** 全機種共通（`*` / `general`）で検索（既存フィルタ方針を維持）
- 機種がないとき:
  - 仕様の一般確認など → 検索可。結果は「機種未指定のため一般資料中心」と明示
  - 症状・不具合系 → まず聞き返しで機種を聞く。それでも無い場合は一般資料のみ候補にし、**当該機種の断定はしない**

### 曖昧症状（例）

次のいずれかに近く、**対象部位・状況の手がかりが薄い**とき → 聞き返し:

| パターン例 | 追加で聞きたいこと |
|---|---|
| 振動 | 何が／いつ |
| 騒音・音 | 何が／いつ／どんな音 |
| 動かない・停止 | 何が動かないか／エラー有無 |
| 〜できない（開かない等） | 何ができないか／機種 |

仕様確認っぽい具体質問（「火災管制の動作は？」「○○の寸法は？」）で機種がある場合は、聞き返さず検索してよい。

### 実装メモ

- v0: キーワード＋機種有無の単純判定で十分  
- 「聞き返し専用の長い LLM」は作らない  
- チャット履歴に直前の聞き返しがある場合は、ユーザー追記を結合して再検索

## 5. ページ表示（API / UI）

### 現状（v0 実装後）

- `pageCandidates` / `sourceDocuments` に `pageNumber` を付与（KB メタがあるときだけ）
- Bedrock KB の `x-amz-bedrock-kb-document-page-number` 等を読む。無ければキー省略＝UI「ページ不明」
- 本番メタ有無の確認は [verify-checklist-2026-07-29-kb-filter.md](./verify-checklist-2026-07-29-kb-filter.md) / §9

### API 案（後方互換）

`POST /rag/query` レスポンスに追加:

```json
{
  "responseType": "clarify" | "pages" | "not_found",
  "clarifyQuestions": ["機種（または工事番号）", "何が振動していますか？", "いつ発生しますか？"],
  "pageCandidates": [
    {
      "documentName": "....pdf",
      "category": "C資料",
      "modelType": "AXIEZ",
      "pageNumber": 42,
      "sourceUri": "https://...(presigned)",
      "relevance": 0.81,
      "snippet": "（任意・短い抜粋）"
    }
  ],
  "content": "（短文。clarify/not_found では定型文でも可）",
  "sourceDocuments": [ "...既存互換..." ]
}
```

- `responseType=clarify` のとき `pageCandidates` は空、検索しない  
- `pages` のとき UI は **候補リストを本文より上** に出す  
- `not_found` のとき作文で埋めない  
- 既存の `content` / `sourceDocuments` は残し、フロント段階的対応

### UI 案（chat）

1. `clarify` → 聞き返し文＋質問リスト（入力欄はそのまま）  
2. `pages` → 候補カード（資料名・**p.N**・開く）を上部に固定的に表示  
3. PDF を開く: まずプリサイン URL（ページ指定 `#page=N` はビューア次第。最低限「p.N を見て開く」で成功条件は満たせる）  
4. 機種未選択時は送信前に軽い注意（必須化は v0 で強めてよい）

## 7. 弱い検索ゲート（v0）

既存 `is_weak_retrieval`（例: top score < 0.22）を **本当に使う**。

- 弱い → Claude に長文生成させない  
- `responseType=not_found`  
- 「機種・症状を具体化して再検索」を促す

閾値は後で現場ログで調整。初期は厳しめでよい（誤答より「無し」）。

## 10. 受け入れ条件（v0）

凡例: ✅ コード済（単体／実装確認）／ ⬜ 本番・手動シナリオ未確認

- [x] 「振動」「騒音」「動かない」「〜できない」＋機種なし → 原則聞き返す（無理に断定しない）。一般資料だけの候補にする場合は機種固有と偽らない ✅
- [ ] 機種あり＋具体化後 → C/TI/据付基準から候補が出る（または not_found）。機種指定時も全機種共通資料は候補に含めうる ⬜（本番 KB で確認）
- [x] 機種なしの一般的な仕様確認 → 検索してよい（一般資料）。「機種未指定」と明示 ✅
- [x] 候補に **資料名＋開く** が出る。ページ番号はメタがある場合のみ（無い場合は「ページ不明」。捏造しない） ✅
- [x] 弱い検索で見当違いの長文が返らない ✅
- [x] 聞き返し後の追記は直前質問と結合して再検索する ✅
- [ ] 現場代理人が候補から **該当資料** を開き、疑問の判断材料に辿れる（手動シナリオで確認） ⬜
  - 頁ジャンプ（`#page`）は当面必須ではない
