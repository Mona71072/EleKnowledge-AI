# 決定: PR 会話がルールどおりに見えなかった原因と直し方

> **状態:** ドラフト（共同確認用）  
> **日付:** 2026-09-10（追記 2026-09-12）  
> **関連:** `AGENTS.md` v1.3.8 / `docs/ops-ai-driven-dev.md` §6c / `.cursor/rules/pr-clarity.mdc` / `.cursor/skills/joint-pr-review/SKILL.md`

## 何が起きたか

未マージ PR の多くは、マージ担当欄はあるが **会話になっていなかった**。

- itai 側（多くは Claude Code の PR 機能）: 概要＋「マージ担当: itai / マージ可: mona の Approve」。相手呼び出しも Yes/No も無い
- mona 側の古い実装 PR（#74–#78）: メンションもマージ担当も無く、コメントで「#78 より先にマージ」と偽の順番を書いていた
- レビュー: Mona-mebs が技術指摘を `CHANGES_REQUESTED` として直接投稿。中身は有用だが、製品判断・マージ可まで人が見ていないことがある

## なぜ起きたか

1. **会話ルールが Cursor にしか無かった。** `pr-clarity` と `joint-pr-review` は Claude Code が読まない。Claude Code が見るのは `CLAUDE.md` → `AGENTS.md`
2. **`AGENTS.md` が「細かく分ける（AI レビュー効率優先）」だけだった。** Cursor 側の「同種はまとめる」と食い違い、PR 機能は小さい PR を量産する
3. **`CLAUDE.md` が要約を持ち、古くなっていた。** 「PR は細かめ」と古い docs 一覧があり、Claude Code だけが古い運用に従う
4. **GitHub テンプレを `gh pr create` の自作本文がスキップする。** 「Generated with Claude Code」本文はテンプレを使わない
5. **マージ担当の Must 化（v1.3.6）だけが AGENTS.md に入った。** エージェントは欄を埋めて合格したつもりになる。Yes/No が無い
6. **「是正できるところは勝手に」の解釈。** 再現できる技術ブロッカーを投稿すること自体は開発に効く。マージ可や製品判断まで代行すると会話が消える

## 当時直したもの / 当時直さなかったもの

**当時直した（再発防止・自側）→ 結果**

- `AGENTS.md` に「PR の会話」を置き、Claude Code からも見えるようにする → **#103 として 2026-09-11 に `develop` へマージ**
- `CLAUDE.md` から古い一覧と「細かめ」を外し、ポインタだけにする → 同上
- GitHub テンプレに Yes/No と「相手を呼ぶ」を足す → 同上
- mona 側の止まった PR（#74–#78）本文を、会話できる形に直す（偽のマージ順を撤回）→ 本文修正のあと、**2026-09-10 に #73–#78 を Close**（置き換え済み。マージしない）

**当時直さなかった（触ると開発が悪くなる）**

- itai の進行中 PR 本文をテンプレ是正で書き直さない（レビューと修正コミットが動いている）
- 技術的な `CHANGES_REQUESTED` を取り消さない（保持期間スクリプト等の指摘は残す）
- 同種 PR を今から無理に 1 本へ統合しない（進行中レビューを壊す）

## ルールを変えた判断

今のルールを絶対視しない。良い開発になる方へ直す。

| 旧 | 新 |
|---|---|
| PR は細かく分ける | 相手が判断できる単位。同種は寄せる |
| デプロイ PR は必ず `@yukiworkspace` | **相手を呼ぶ。** 自分宛てメンションは不要 |
| マージ可の条件 = mona の Approve | Approve は内容OK。マージ可は別に書く。Yes/No を1つ以上 |
| レビューは投稿前に全部聞く | 技術ブロッカーは投稿してよい。判断は人に聞いてから |
| Cursor 短則が会話の正 | **`AGENTS.md` が全ツールの正。** 短則は要約 |
