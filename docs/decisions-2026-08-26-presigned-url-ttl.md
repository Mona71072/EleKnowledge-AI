# 引用文書の署名付き URL TTL と旧 URL の扱い（2026-08-26 決定）

> **状態:** 決定記録（PR #50 実機確認後のユーザー決定）
> **前提:** 引用リンクのログイン必須化（PR #50、中継ページ `/doc` 方式）の実機確認は 2026-08-26 に完了・正常動作。本記録はそこで確認された残課題 2 点への対応判断を残す。

---

## 1. TTL の変遷

| 時期 | TTL | 経緯 |
|---|---|---|
| 初期実装 | 30日（トラブルシューティング系は SigV4 上限 7 日超で実際には無効） | 深く考えずに長期を指定。コードレビュー 2026-07-29 H-2 で指摘 |
| PR #48 | 1時間（3600秒） | セキュリティ監査 2026-08 を受けて短縮。ただし URL は依然メッセージと共に DynamoDB へ保存されていた |
| **本決定** | **300秒（5分）** | PR #50 でクリック都度発行（`GET /rag/document`）になり、保存されるのは `s3://` URI のみ。発行済み URL は「開く瞬間」にしか使われないため、長い TTL を維持する理由が消えた |

- 変更箇所: `infrastructure/sam/phase2-template.yaml` の `PresignedUrlExpiresIn` Default（3600 → 300）と、`lambda/rag/rag-function/app.py` の env フォールバック既定値
- 300 はテンプレートの `MinValue` と同値（＝許容最小）。大きな PDF でも「リンクを開く」操作自体は数秒であり、5 分で不足する状況は想定していない

## 2. 残存リスク: 発行済み URL の流出（実機確認 2026-08-26）

ログアウト後でも、発行済みの署名付き URL をコピーしていれば有効期限内は開けることを実機で確認した。

- S3 の署名付き URL は**ベアラー URL**であり、失効前に取り消す手段がない（構造的限界）
- したがって対策は「発行を認証で守る（#50 で対応済み）」＋「TTL で露出窓を絞る」の 2 層になる
- 本決定後の最大露出は **300 秒**（流出した瞬間から最悪 5 分間だけ開ける）

## 3. 旧署名付き URL の逆変換（過去チャット履歴の扱い）

#50 以前のメッセージには発行済み署名付き URL（TTL 1h）がそのまま DynamoDB に保存されており、期限切れで S3 の AccessDenied (Request has expired) になっていた。

**決定:** フロントの `documentHref` で旧署名付き URL を検出し、bucket/key を `s3://` URI に逆変換して中継ページ `/doc` 経由に流す。

- virtual-hosted 形式（`https://<bucket>.s3.<region>.amazonaws.com/<key>?X-Amz-...`）とパス形式（`https://s3.<region>.amazonaws.com/<bucket>/<key>?...`）の両対応。署名クエリは捨てる
- 効果は 2 つ:
  1. **過去履歴の引用が復活する**（期限切れ URL でも都度発行に乗せ替わる）
  2. **保存済み URL の流出リスクを塞ぐ**（DynamoDB に残った旧 URL はどのみち期限切れで、リンクとしても認証必須の `/doc` を通る導線に置き換わる）
- S3 と判定できない https URL は従来どおり素通し。URL パース失敗時も throw せず素通し（**安全側設計**: 誤検出で開けなくなるより、判定できないものは触らない）
- DynamoDB 側の旧データは書き換えない（表示時に変換するだけ。データ移行は不要）

## 4. 期限切れプリサイン URL への直接アクセス時の想定挙動

正規導線では期限切れ URL にユーザーが遭遇しない設計とする（保存・共有・クリックされるのは `/doc` 中継リンクのみで、プリサイン URL はクリック時に発行してその場で使い捨てる）。

それでも発行済み URL に期限後アクセスした場合（開いたタブのリロード・ブラウザ履歴からの再訪・コピーされた URL の再利用）:

- **S3 が素の 403 XML（`AccessDenied` / `Request has expired`）を返すのが想定動作**とする。リクエストはブラウザ → S3 に直行し、アプリ（Lambda / フロント）は経路上に存在しないため、フレンドリーなエラーページや再発行リダイレクトを差し込むことは構造的に不可能。`/doc` ページのエラー UI が拾うのは発行 API（`GET /rag/document`）の失敗まで
- **復旧導線は「チャットの引用リンクを再クリック」**（都度発行で新しい URL が得られる）。これで足りるため、S3 エラーページのカスタマイズ等は行わない
- 既知エッジケース: ブラウザの PDF ビューアはレンジリクエストで大きい PDF を逐次読み込むため、**5 分を超えて閲覧を続けると未読ページの取得が期限切れで失敗しうる**（表示済みページは影響なし）。TTL を 300 秒まで詰めたトレードオフはここに現れる。復旧は同じく再クリック。頻発するようなら TTL の再調整（例: 900 秒）を検討する

API 仕様としての記載は [docs/api/rag.md](./api/rag.md) の `GET /rag/document` 節。

## 5. 将来の代替案メモ（スコープ外）

- CloudFront 署名付き Cookie / 署名付き URL への移行: 失効制御・パス単位の認可がより柔軟になるが、ディストリビューション新設と運用が増えるため今回は見送り
- S3 Object Lambda / API Gateway 経由のストリーミング配信: 完全にベアラー URL を排除できるが、Lambda の 6MB 応答上限と大型 PDF が干渉するため要検討
