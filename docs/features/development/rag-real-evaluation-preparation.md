## 6〜12問の実資料セット作成手順

全ゲート後に技術担当者が6問から始め、各カテゴリ1問以上、最大12問にする。機種指定、故障調査、手順/基準値、法令/規格、技術資料とノウハウ横断、根拠不足/矛盾/旧版/権限外を含める。旧版・別機種は正解根拠ではなく、明示的な誤引用禁止資料として登録する。実業務資料で成立しないカテゴリは無理に合成ケースで埋めず、対象外と理由を残す。

評価問題には、質問ID、質問と前提、機種・型式・部位・状況、期待する回答または`hold`/`clarify`、正本資料別名と文書ID・版・発効日、正解箇所（ページ/節等）、禁止資料、資料種別、所有者、利用許可記録ID、担当技術者の確認者と日付を持たせる。原文の引用は安全な保管先の参照先で管理し、Gitには含めない。雛形は[実資料レビューラン雛形](../../../tests/eval/templates/real-rag-review-run.template.json)を参照する。雛形のplaceholderを正本資料へ置換し、質問セット版・許可記録・評価者を固定してから実行する。

## 人手採点・裁定手順

1. 評価責任者がデータ許可、アクセス制御、保存期限を確認し、許可済み資料だけの読み取り専用セットを固定する。
2. 同じ質問、同じ資料スナップショット/KB同期状態、同じ検索設定、Top-K、対象HEADでRetrieveを実行する。取得件数制限、質問回数、費用上限を事前に固定する。
3. 採点者2名は出力や互いの判定を見ずに独立採点する。資料正本と該当版の正解箇所に照合する。LLM採点を使う場合も参考値に留める。
4. 適用機種・版・部位、条件、各回答主張、引用資料、資料種別、主張を支持する箇所を個別に判断する。ID一致だけで支持としない。
5. 不一致を正本根拠に戻って確認し、裁定者・理由・変更前後の判定を残す。重大失敗は平均スコアに関係なく受入ブロッカーとする。
6. 実資料本文・個人情報・機密質問をGitHub、PR、通常ログ、許可のない外部AIへ記録しない。データを安全な評価保存先へ置く。

分母は評価対象ごとに固定する。検索根拠のRecallは期待根拠数、Top-K Recallも同じ期待根拠数、汚染率は全取得文書数を分母にする。回答支持率・引用漏れ・スコープ一致率は事実主張数、条件記載/支持/省略率は適用条件数、保留適切率は保留を期待した質問数、法令混同率は法令関連質問数を分母とする。0件の率は`null`。未判定は成功にしないで未判定数として報告し、裁定後に確定した値のみ最終率へ含める。2名一致率は全独立判定項目数と一致数を併記し、重大項目はCohen's kappaも参考値として報告する（低母数では率の不安定性を併記）。

## T21 合成候補プール比較

コマンド: `python scripts/eval/compare_t21_candidate_strategies.py --fixture tests/eval/fixtures/t21_synthetic_candidates_v1.json`

同じ合成候補21行・20個の文書/ページ群・候補上限10・正解根拠2件を固定し、外部呼び出し0で比較した。これは保存済みの実検索候補ではない。

| 方式 | 正解根拠保持 | 観察 |
|---|---:|---|
| A 全体スコア順 | 0/2 | 2つとも上位10群から落ちるように構成した再現例 |
| B レーンごと5件枠 | 1/2 | 片方を戻すが別の必要根拠が落ちる |
| C 重複排除後に全体順位 | 0/2 | 現行経路も重複排除を行う。重複排除だけではこの候補プールの脱落は直らない |
| D 機種+版フィルタ | 2/2 | 理想化された合成ラベル。実索引のメタデータ完全性・利用可能性は未確認 |
| E 固定再ランキング値 | 1/2 | モデル呼び出しなしの合成値でもう一方が落ちる |

**判定:** 全体Top-10選別が候補脱落を起こし得る機構は合成データで再現した。ただし過去の「全体12位」事例を実ログで再現しておらず、現行システムの実検索品質の欠陥や本番改善量を証明していない。レーン枠は必要資料の別の脱落を招くため、そのまま採用しない。メタデータフィルタは完全性・権限漏れ・版履歴を実測してから検討する。再ランキングは候補を入れ替えるため単独採用しない。**現状は本番セレクターを変更しない。**

実候補が得られたら、同一クエリ・同一候補プール・同一K/呼び出し回数・同一費用制約で全方式を比較し、全正解根拠の保持と、誤版/誤機種/無関係/未認可候補の混入を同時に採点する。

## AWS最小実機試験

AWS接続後も、まず読み取り専用`Retrieve`だけを行う。`Retrieve`要求の質問文字列はAWSへ送信され、取得チャンク本文/メタデータが返るため、質問送信と応答取得の両方の許可が必要である。Bedrock公式資料はRetrieve-onlyとRetrieve-and-generateを別評価として扱い、前者のContext relevance/coverageと後者のFaithfulness/Citation指標を分ける。評価ジョブと採点モデルは有料利用・データ送信範囲を別途承認後にする。[Bedrock評価の種類](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)・[評価指標](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-evaluation-metrics.html)・[Retrieve APIとGuardrails適用範囲](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve.html)

最低限記録するもの: アカウント別名（生のアカウントIDは制限保存）、リージョン、KB ID、データソース別名、同期状態/版、質問ID、検索フィルタ、K、取得文書別名/版/rank/score、応答時間、モデル呼出しの有無（Retrieveのみは生成モデル呼出し0）、データ分類、実行者、評価ファイルの保存先アクセス制御。検索チャンクの原文を一般ログに出さない。Guardrailsは取得参照そのものに適用されないため、権限制御・分類ラベル・検索結果のプロンプトインジェクション耐性は独立した受入項目とする。
