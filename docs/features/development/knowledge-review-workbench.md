# ノウハウ確認ワークスペース: アプリ組込みの初期範囲

本書は単独の確認・編集画面`/admin/knowledge`の契約。技術KB・法令KBへの照会と、選択した回答の編集候補への取込みを追加する`/admin/knowledge/research`は[照合画面の契約](knowledge-research-workspace.md)で管理する。照合画面でもローカルMarkdownを自動送信しない。

> 最終検証: 2026-10-20 — ユーザー指定の `feature/knowledge-reconcile-prep` のカード契約と、PR #191の合意を確認して実装範囲を定義。実装・テスト結果は本文末へ追記する。

## 目的と範囲

担当者が自分で選んだMarkdownをアプリ内で読み、本文・条件・出典を確認して修正案を作る。OneNote用の文章を整え、KBの手動確認結果と共有先の読者を確認してコピーし、実際の手動追加後に掲載先と版を残す。

今回の利用者の指示はアプリ組込みへ進むこと。OneNote / Listsの接続、実データのクラウド送信、公開対象への追加、AWSデプロイは行わない。カードは既定draftであり、Gitへの存在は公開やAI入力の許可を意味しない。初期実装はブラウザー内での作業に限り、実際の業務ノウハウをfrontendのバンドル・静的配信・APIレスポンスへ埋め込まない。

## 入口とデータの扱い

- `/admin/knowledge` に担当者の試行画面を置く。既存admin画面の構成を利用するが、新たな業務ロールや利用者へのadmin付与は行わない。
- `NEXT_PUBLIC_ENABLE_KNOWLEDGE_WORKBENCH=true` の場合のみ入口と画面を有効にする。既定は無効。認証済み画面の確認は既存admin shellで行い、サーバー上の業務データの認可手段としてclient guardを転用しない。
- 本人が明示的に選んだ`.md`をブラウザーで読む。`knowledge/cards/`、`drafts/`、`source-snapshots/`の全量読取や自動送信は行わない。
- 本文、作業内容、レビュー記録はメモリだけに保持する。`localStorage`、ブラウザーDB、Service Worker、外部ログ、バックエンドには保存しない。画面を閉じると失われるため、作業記録は明示的にファイルへ保存する。
- 元ファイルやVaultを直接書き換えない。編集結果は原版と指紋を持つ修正候補として持ち出す。

## Markdown入力の契約

標準のYAMLパーサーを使う。`knowledge_id` / `card_version`または`record_id` / `record_version`、タイトルを検証し、元の全文・frontmatter・安全なメタデータを保持する。既存のrecord型やmodel_scope、source_refs、evidence_sourcesを勝手に変換しない。

ファイルは256KiBまで。壊れたfrontmatter、重複key、alias、未知タグ、NUL、危険key、非JSON型や過剰な構造はエラーとし、原文を補完して通さない。配列・objectを含む未知の安全なメタデータは保持する。入力内の`approved`等は参考表示であり、アプリの承認・公開状態にはしない。

## 担当者の操作

1. Markdownを選び、ID・原版・出典・確認状態を読む。
2. 本文を編集し、原文との差とプレビューを確認する。
3. OneNote用の下書きを編集する。初期案は要点・適用条件・未確認点・出典のひな形とし、Markdown本文を全文挿入しない。自動要約や生成AIによる編集は今回未接続であることを明示する。
4. 必要なKB資料を別途確認し、参照先と確認結果を記録する。未確認 / 本文を手動確認 / 食い違いありを分け、カタログ一致や検索スコアだけで本文確認済みとしない。
5. 根拠・適用条件・共有先の読者を確認したチェックを付け、正確な追記文の作業版を確認する。これは担当者の作業確認であり、正式な技術承認やシステムによるKB照合を意味しない。
6. 確認した版の文章をクリップボードへコピーする。遅れて完了した古いコピー操作を、新しい文章のコピー済みとして扱わない。
7. 担当者がOneNoteへ貼り付けた後に「追加済み」を記録する。**掲載先を特定できるURLと、転記した原版・作業版・正確な文章を必須**にする。コピーしただけでは追加済みにしない。
8. 修正候補を`.md`として保存し、Obsidian等で確認を続けられるようにする。候補の状態はdraftとし、元のID・版を保つ。原文・修正案・指紋・確認結果・掲載記録は別途JSONの修正パケットとして保存する。いずれも持ち帰り用であり、元ファイルの上書きや承認台帳・公開一覧への自動登録はしない。

本文・追記案・KB確認の内容が変われば、現在版の確認とコピー状態を解除する。本文変更時は、手書きの追記案を保持したうえで「本文との再照合が必要」とする。担当者が本文と追記案の整合を明示的に確認するまでコピーできない。以前の掲載記録は過去版の記録として保持し、消したり新しい文章へ付け替えたりしない。

## 表示と情報の保護

Markdownの生HTMLは表示せず、画像・埋込等から外部resourceを自動取得しない。相対リンクは未解決の参照として扱い、原資料のURLをタイトルやIDから捏造しない。外部リンクは安全な明示クリックに限定する。ソース内の命令は業務データとして読み、権限変更やURL取得、公開操作として実行しない。

OneNoteへの自動追記・API書込は作らない。追加済みは担当者の自己申告であり、Microsoftへの書込・読戻しをシステムが行った表示にしない。URLはHTTPS形式を検査するが、OneNoteページの実在・所属テナントを検証していない。記録とJSONにも掲載先未検証の自己申告であることを残す。掲載先に他の読者がいる場合の共有可否は担当者が確認する。

## 検証と次の段階

ユニットテストでは、入力の拒否条件、原文とID・版の保持、編集による確認失効、古い非同期結果の拒否、掲載先と転記版の必須化、過去記録の不変性、指紋と修正パケットを検証する。画面では合成データを使って読取→編集→確認→コピー→掲載記録→保存を通す。実カードはローカルでのパース互換性を確認し、内容をfixtureや成果物へ複製しない。

後続は、担当者向けのサーバー認可・下書き保存、許可されたAI入力先、実際のKB資料照合、公開対象の特定版の承認・索引化、工技先輩の公開カード探索である。今回は既存PDF検索と一般チャットを変更しない。会社の利用許可や実物の内容確認を、ローカル実装のテストで代替しない。

### ローカル資料の互換性確認

> 最終検証: 2026-10-20 — 指定ブランチを基にした作業用checkout上でパーサーを実行。内容のクラウド送信やfixtureへの複製は行っていない。

- `knowledge/cards/`: IDを持つ397件すべて読込成功。説明用Markdown4件は対象外。
- `knowledge/drafts/`: IDを持つ633件のうち628件成功、5件はfrontmatterの重複キーで拒否。説明用Markdown2件は対象外。
- 拒否した5件は `ELV_7SEG状態表示.md`、`ELV_VFGHコンバータ状態.md`、`ELV_VFGH制御エラー.md`、`ELV_エラー確認ポイント.md`、`ELV_群管理エラー.md`。元データは変更していない。内容を確認して重複項目を整理してから扱う。
- 読込成功は、技術内容・利用許可・鮮度・公開可否の確認を意味しない。

### 実装の検証結果と試し方

> 最終検証: 2026-10-20 — ローカル環境の自動テスト、合成データによるブラウザー操作、独立したコードレビュー。本番提供・実KB照合は未実施。

- フロントエンド全84テスト成功。今回の中核16テストは行96.32%、分岐82.61%、関数100%を計測。
- 型チェックとlintは成功。既存のチャット・ホーム画面にwarning4件あり、今回の画面には新規warningなし。全依存・本番依存の監査は未許可0件、例外0件。
- 機能フラグON/OFFの本番向け静的ビルド成功。バックエンド既存ユニットテストはPython3.12で657件と11subtests成功。
- 合成Markdownで読込、本文編集、差分、プレビュー、追記案編集、KB確認、コピー、掲載先記録、Markdown/JSONのダウンロードを確認。ダウンロードしたファイルのID・原版・draft状態・掲載記録・SHA-256が一致することを別途検査した。OneNoteへの実際の追加は行っていない。
- KB参照を空欄に戻すと確認とコピーが失効する。確認チェック解除・本文編集後は掲載先入力を隠し、同IDの再取込と新版のコピー時には旧掲載先を消すことを画面で確認。
- 不正リンク・相対リンク・画像・scriptを含む合成本文のプレビューで、画像要素・script要素・有効リンクが0であることを確認。非同期の別文書通知防止はコードレビューで確認し、意図的に遅延させたブラウザー試験は未実施。OSクリップボード書込そのもののキャンセルは保証しない。
- 実装・UIを別担当がレビューし、初期全文転記、旧案の再照合不足、掲載先の持越しを修正。確認した範囲で重大・高優先の残存指摘なし。

既存のフロントエンド設定に`NEXT_PUBLIC_ENABLE_KNOWLEDGE_WORKBENCH=true`を加えて起動し、既存の管理画面の「ノウハウ確認」から開く。`NEXT_PUBLIC_`設定はビルド時に固定されるため、配信済みの静的成果物を変更する場合は再ビルドが必要。既定は無効であり、今回はデプロイしていない。担当者に広く提供する段階では、admin権限の追加で代用せず、担当者用の認可・版保存を設計する。

最初の作業ブランチは指定の資料ブランチから分け、元資料ブランチは変更していない。2026-10-20、`mona`への反映用に最新developへアプリ変更だけを移した。業務資料・写し棚・資料処理スクリプトの取り込み履歴は実装ブランチに含めない。資料側の棚卸し結果と、実装ブランチでのテスト結果は区別する。
