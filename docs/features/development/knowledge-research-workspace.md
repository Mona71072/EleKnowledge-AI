# 工技先輩の開発画面：ノウハウ・技術KB・法令KBの照合

## 目的と完成条件

開発中の独立した画面で、選択したノウハウMarkdownを読み、技術KBと法令KBを調べ、根拠を比較して編集案を作る。最終目標は、三つの情報源を条件・出典付きで活用できる、実際に使えるアプリである。画面表示やモック試験だけで最終目標を完了としない。

段階的に、(1)両KBへの実API接続と出典別の比較、(2)選んだ結果のMarkdown編集案への取込み、(3)許可された開発環境で実検索と出典閲覧、(4)適用条件・食い違いを扱う統合支援と評価を進める。通常・法令の回答を単に並べた状態を「統合AI回答」と呼ばない。実環境の検索・閲覧・適用確認は未検証として残す。

## 今回実装する接続

- `/admin/knowledge/research`は担当者の調査・Markdown編集画面、ユーザー画面側の`/knowledge/chat`は会話を続ける「先輩チャット」とする。通常ホームではRAGチャット・法令チャット・トラブルシューティングに続く4つ目のカードとして設ける。法令カードは既存の有効化条件を維持するため、無効環境では表示枚数は減る。先輩カードの入口は管理者かつ`NEXT_PUBLIC_ENABLE_KNOWLEDGE_WORKBENCH=true`の場合だけ表示し、一般ユーザーには予告カードも表示しない。既存admin利用者の試行用であり、新しい利用者へのadmin付与はしない。
- `/knowledge/chat`は既存`AdminOnlyGuard`で囲み、管理者確認中・未認証・非管理者にはチャットUIをマウントしない。未認証はログインへ誘導し、非管理者は権限案内とホームへのリンクを表示する。フラグOFFなら管理者にも無効の案内だけを表示する。通常のホームへ戻れる専用チャットとし、Markdownの選択・編集を会話の前提にしない。これらは画面の表示制御であり、既存APIのJWT認証・userId分離を代替しない。静的配信のコードを秘密にする仕組みでもない。
- 技術KBと法令KBは既存`POST /rag/query`へ、同じ明示入力の質問を`mode: normal`と`mode: law`で並列送信する。CognitoのID tokenをAuthorizationに使い、userIdを本文へ追加しない。モード間でsessionIdを共有しない。
- 担当者の調査・編集画面は毎回独立した問い合わせとする。先輩チャットは初回に作った通常・法令それぞれの`sessionId`を次の発言でも使い、既存APIが保持するモード別の会話文脈を引き継ぐ。APIが作る履歴は通常・法令それぞれ別であり、既存の60日保持対象となることを送信前に表示する。
- ローカルMarkdown・OneNote案・メタデータ・ファイル名を自動送信しない。送信対象は質問欄だけ。資料をもとに質問する場合は利用者が質問欄へ必要な内容を入力して確認する。
- 各回答は独立した出典欄に表示する。一方が未設定・403・タイムアウト・検索失敗でも、成功側を利用できる。未収載とAPI利用不可を区別する。法令が失敗しても技術KBで代用しない。
- 質問は空白以外1〜2000文字。設定不足・未認証・不正な応答は日本語で案内。通信と認証待機には上限を設け、中止・新規検索・画面終了後の古い応答で現在の結果を上書きしない。中止してもサーバー処理・履歴保存そのものの取消は保証しない。

## ユーザー画面の先輩チャット

- 質問と返答が時系列の吹き出しとして残り、同じ画面から補足・追加質問を送信できる。各返答の技術KB・法令KBの本文と出典は分けて表示する。二つを単に並べた返答を、AIが統合・技術承認した回答とは扱わない。
- 送信本文は`query/mode/filters`と継続時だけの`sessionId`に限定する。会話全文・Markdown・ファイル名・userIdは送信しない。既存APIがJWTの所有者とsessionのモードを照合してから履歴を取得する。初回の通信契約を変更しない。
- `queryKnowledgeSource`は省略可能な`sessionId`を受け取り、空・128文字超・制御文字を拒否する。継続要求への応答が別sessionIdなら不正応答として扱い、別履歴へ無断で切り替えない。
- 通常・法令のsessionIdを共有せず、同じ会話中は各モード固有のIDを保持する。片方の失敗でも成功済みの返答は残す。失敗・中止・タイムアウトで保存状況が分からない側は、文脈を飛ばしたまま続行せず「新しい相談」まで休止し、利用者に案内する。利用可能な側には続けて質問できる。
- 「中止」は実行中の側だけを止め、到着済みの返答を残す。「新しい相談」は待機を中止して吹き出し・sessionId・休止をリセットする。旧応答や画面終了後の応答を新しい相談へ書き戻さない。二重送信を防ぐ。中止してもサーバーの履歴保存・処理取消は保証しない。
- ページの再読込・終了で先輩チャットの組み合わせ表示は消える。各モードのAPI履歴は既存チャットのリンクから確認できる。統合履歴の保存先やOneNoteへの書込みを新設しない。必要な場合に担当者の「ノウハウの確認・編集」画面へ進める。

受入条件は、カードが既存3機能の後に並ぶこと、管理者だけが使えること、同じ画面で2往復以上の質問・回答が残ること、2回目に各KB固有のsessionIdが送られること、新しい相談ではどちらの旧IDも送られないこと、片側停止・中止・旧応答の競合で履歴が混ざらないことである。ローカル架空データの検証と会社ネットの実KB受入を区別する。

## 出典と編集

技術資料は既存の認証付き`/doc`経由で開く。S3の署名付きURLを持ち帰りファイルやリンクへ残さず、S3 URIへ戻して中継する。法令は応答にある法令名・条文・施行日・e-Gov出典を表示し、HTTPSのe-Gov法令URLだけを有効にする。日付や条文番号、リンクのアンカーを推測しない。API応答の生HTML・埋込・画像を実行しない。

生成するMarkdownの技術資料URIと対象ノウハウIDは、バッククォートを含む値でも文字通りのコードとして保持する。値をHTMLや画像・リンクの構文として展開しない。アプリのプレビューだけに依存せず、持ち帰り先のMarkdownでも同じ境界を保つ。

「編集案へ取り込む」で、選択した回答と出典を調査メモとしてローカルMarkdown本文へ追記する。これはAI回答の採用候補であり、技術承認・法的判断・KB本文の人手確認ではない。照合済みチェックを自動で付けない。本文編集と同じ版失効を通し、OneNote案との再照合を必要にする。元ファイル・OneNoteへ自動書込みしない。

取り込み先は検索開始時の文書セッション・ID・原版・本文の作業版へ紐付ける。文書の再取込・別文書への切替・本文の手編集後は旧結果を表示できても取込み不可とし、再検索を案内する。ファイル未選択での調査は閲覧用であり、後から選んだファイルへ無警告で適用しない。同一検索の技術・法令両メモを順に追加する操作は許容し、その既知の追記だけでは相手側の結果を失効しない。取り込み先の条件を変える本文手編集は必ず失効させる。

調査メモには検索モード・質問・クライアント受信日時、APIが返す回答日時（有効な場合）、sessionId/messageIdも追跡情報として残す。これらはAI回答の追跡用であり、資料の改訂版や技術承認の識別子ではない。API履歴は60日で失われ得るため、採用時の本文と出典も併せて保持する。

### 担当者による照合まとめ

同じ質問・対象本文で得た両方の回答を、担当者が「一致している / 条件が違う / 食い違いあり / 判断保留」に整理できるようにする。初期値は判断保留。これはAI回答の比較メモであり、原資料本文の確認・技術承認・法的判断として扱わない。

- 比較して分かったことと適用条件・対象外を必須入力とし、それぞれ4000文字まで。判断保留・食い違いありの場合は未確認事項・次に確認することも必須。いずれの文章も自動生成・自動送信しない。
- 同じ質問のnormal/law各1件で、両方が根拠リンクを持つ回答の場合にだけ保存可能。片側失敗・未収載・聞き返し・別質問・別文書・手編集後の旧回答は使わない。
- メモは回答ペアと対象本文の版に紐付ける。再検索・文書再取込・本文手編集で以前の入力・取り込み済み表示を破棄し、新しい回答へ持ち越さない。片側の回答が更新されても同様。
- 「照合まとめをMarkdownへ取り込む」で、入力した比較内容・条件・保留事項と、両回答の本文・出典・追跡情報をローカルの修正候補へ追記する。未知の項目を「なし」「解決済み」と補完しない。Markdown構文やHTMLを入力しても構造の外へ実行・展開しない。
- 親の編集状態への追記成功を受け取ってから取り込み済みと表示し、同一内容の重複クリックを防ぐ。入力変更後は別の作業メモとして再取込み可能。追記失敗時に取り込み済みと表示しない。
- 既存の本文編集と同様、KB手動確認・OneNoteの確認/コピー状態を失効させる。本文へメモを追記しただけでは、食い違いの解消・公開・承認を成立させない。

`buildComparisonNote({technical, law, assessment})`を純粋関数として実装し、型付きの`assessment`は`status: consistent|conditions_differ|conflict|unresolved`、`findings`、`applicability`、`unresolvedPoints`を持つ。UIは既存の文書対象キーを使い、親への`onAdopt`が返す成功/失敗を確認する。

## 実装の分担と契約

`knowledge-research.mjs`は`queryKnowledgeSource({baseUrl, getToken, fetchImpl?, mode, query, signal?, timeoutMs?})`、`researchSourceHref(source, mode)`、`buildResearchNote(answer)`を公開する。API応答は`content`、`responseType`、`sessionId`、`aiMessageId/messageId`、`sourceDocuments`、`pageCandidates`、`clarifyQuestions`を検証して正規化し、`.d.mts`で型を共有する。

`KnowledgeResearchWorkspace`は検索と結果表示を担当し、`KnowledgeWorkbench`の編集状態を正本とする。任意の`research`モードで編集画面に検索欄を表示し、採用操作だけを既存`editBody`へ渡す。API認証や検索結果から公開・レビュー状態を生成しない。
