# 工技先輩の開発画面：ノウハウ・技術KB・法令KBの照合

## 目的と完成条件

開発中の独立した画面で、選択したノウハウMarkdownを読み、技術KBと法令KBを調べ、根拠を比較して編集案を作る。最終目標は、三つの情報源を条件・出典付きで活用できる、実際に使えるアプリである。画面表示やモック試験だけで最終目標を完了としない。

段階的に、(1)両KBへの実API接続と出典別の比較、(2)選んだ結果のMarkdown編集案への取込み、(3)許可された開発環境で実検索と出典閲覧、(4)適用条件・食い違いを扱う統合支援と評価を進める。通常・法令の回答を単に並べた状態を「統合AI回答」と呼ばない。実環境の検索・閲覧・適用確認は未検証として残す。

## 今回実装する接続

- `/admin/knowledge/research`は担当者の調査・Markdown編集画面、ユーザー画面側の`/knowledge/chat`は会話を続ける「先輩チャット」とする。通常ホームではRAGチャット・法令チャット・トラブルシューティングに続く4つ目のカードとして設ける。法令カードは既存の有効化条件を維持するため、無効環境では表示枚数は減る。先輩カードの入口は管理者かつ`NEXT_PUBLIC_ENABLE_KNOWLEDGE_WORKBENCH=true`の場合だけ表示し、一般ユーザーには予告カードも表示しない。既存admin利用者の試行用であり、新しい利用者へのadmin付与はしない。
- `/knowledge/chat`は既存`AdminOnlyGuard`で囲み、管理者確認中・未認証・非管理者にはチャットUIをマウントしない。未認証はログインへ誘導し、非管理者は権限案内とホームへのリンクを表示する。フラグOFFなら管理者にも無効の案内だけを表示する。通常のホームへ戻れる専用チャットとし、Markdownの選択・編集を会話の前提にしない。これらは画面の表示制御であり、既存APIのJWT認証・userId分離を代替しない。静的配信のコードを秘密にする仕組みでもない。
- 技術KBと法令KBは既存`POST /rag/query`へ、同じ明示入力の質問を`mode: normal`と`mode: law`で並列送信する。CognitoのID tokenをAuthorizationに使い、userIdを本文へ追加しない。モード間でsessionIdを共有しない。
- 担当者の調査・編集画面は毎回独立した問い合わせとする。先輩チャットは初回に作った通常・法令それぞれの`sessionId`を次の発言でも使い、既存APIが保持するモード別の会話文脈を引き継ぐ。APIが作る履歴は通常・法令それぞれ別であり、既存の60日保持対象となることを送信前に表示する。
- ローカルMarkdown・OneNote案・メタデータ・ファイル名を自動送信しない。担当者の調査・編集画面は質問欄の内容だけを送る。先輩チャットの技術側は`includeKnowhow: true`を追加し、サーバーに取り込まれた許可済みMarkdownを検索・AI処理に使う。[Markdown自動探索の仕様](knowledge-markdown-retrieval.md)に従い、画面に参照カードの版・条件・出典を表示する。
- 各回答は独立した出典欄に表示する。一方が未設定・403・タイムアウト・検索失敗でも、成功側を利用できる。未収載とAPI利用不可を区別する。法令が失敗しても技術KBで代用しない。
- 質問は空白以外1〜2000文字。設定不足・未認証・不正な応答は日本語で案内。通信と認証待機には上限を設け、中止・新規検索・画面終了後の古い応答で現在の結果を上書きしない。中止してもサーバー処理・履歴保存そのものの取消は保証しない。

## 既存カードの出典確認と編集

> 最終検証: 2026-11-14 — 合成カードで出典照合、本文編集、MarkdownとJSONの保存、補助ツールの初期表示と開閉後の編集内容の保持をブラウザーで検証。Lists・OneNoteのローカルの写しの互換性は11月13日に確認。

カードを開くと、本文編集、出典確認、節へのコメントと追記案、下書き保存を同じ画面から操作できる。一括照合、単発のKB検索、原版の出典一覧、OneNoteへの追記案は必要なときに開く。閉じて開き直しても、同じカードの照合結果や入力途中の作業を復元できる。

初期段階では、管理者が既存のカードを1枚選び、技術KBの原資料、OneNote、Listsを照らし合わせてカード本文を直す。技術KBは既存の検索と資料ビューアを使う。OneNote・Listsは担当者が原資料を開いて確認するか、自分で選んだローカルMarkdownの写しを照合する。カードの出典IDでOneNoteのページやListsの1項目を照合し、別のページや項目を取り違えない。ローカルの写しはブラウザー内で表示する。

出典、資料の版・ページ等の参照箇所、確認結果と判断メモを編集中の版に紐づけて記録し、JSON作業記録に保存する。原文の写しはJSONに含めない。確認結果は担当者の記録として扱う。カード本文は担当者が編集し、差分を確認して下書きMarkdownを保存する。資料改訂を検知して追記・修正の要否を見直す流れは、初期整備の次の段階とする。

## コメントから節を補足する

> 最終検証: 2026-11-14 — 合成資料を使うローカルブラウザーで、差分から節を選ぶ操作、片側の再試行、確認済み追記の反映、JSONの保存と再開を確認。旧v1と本文サイズ上限は単体テストで確認。

Markdownを編集すると、読込時の本文との差分を編集画面内に表示する。差分に原文・修正後の行番号を表示し、追加行と削除行が分かるようにする。既存の節を選び、足りないことをコメントとして残せる。

差分には変更された節の名前も表示する。対象が現在の本文で一意に決まる場合は、差分からその節を選んだ状態でコメント欄を開ける。コメントの照合で片方のKBが失敗または中止した場合は、その照合先だけ再試行できる。成功側の回答・編集中の追記案・採否は保持する。

担当者が送信する検索文を確認してから、技術KB・法令KBに同じ観点で再照会する。送信文はカード題名・節名・コメント・カードに記録された機種の手掛かりと調査の指示で構成する。カード本文、OneNote・Listsの写し、作業記録は送らない。確認できる出典がある応答だけを編集可能な追記案として出す。AI の検索結果をそのままカードには入れない。管理者が出典と適用条件を確認し、追記案（技術KB・法令KBの別）ごとに「確認して追記する」か「追記しない」を選ぶ。既定は未確認で、選ぶまで何も入らない。「確認して追記する」を選んだ追記案だけが差分に出て、コメントで選んだ節の末尾に入る。追記案を編集すると選択は未確認に戻る。カードに入る文面には「原資料未確認」「AI追記案」の表示を付けず、根拠資料の出典リンクと「確認: 管理者が出典を確認（YYYY-MM-DD）」の1行を付ける。出典の無い応答は追記案にできない。反映するまでに本文が変わった場合は差分を破棄し、現在版で再照会できる。

コメントと処理状況はカード本文とは別にJSON作業記録に保存する。「JSON作業記録を開く」で読込時の原文、現在の修正案、コメントを復元して作業を再開する。出典の確認記録やコメントの項目が追加される前に保存したv1の作業記録も開ける。作業記録は本文先頭の空行や編集上限近くの本文を保持し、ダウンロード前に再開時と同じ条件で検証する。実行中の応答や、確認前・追記しないと選んだAI追記案は作業画面で扱い、カードには入れない。追記を取り込んでもカードの技術承認は行わない。

## 現場資料からカード案を作る

> 最終検証: 2026-11-16 — 今回の未回答導線・質問本文の一時引継ぎ・AI同意表示を関連フロントテストと型検査で確認。現場資料の他の動線は2026-11-14付記の検証結果を参照。

先輩チャットと通常の技術KBチャットで、検索完了結果が「見つからなかった」のとき、管理者は照合画面へ移動できる。通常の技術KBチャットでは「ノウハウカードの候補にする」を表示し、照合画面に公式資料検索から開いたことを示す。質問・回答本文・利用者IDは渡さず、担当者が必要な補足を入力する。通信失敗、照会中、条件の聞き返しは対象外。通常チャットの法令モードとじっくり調査はこの導線の対象外。担当者は既存のMarkdownを開くか、タイトルを入力して新しい下書きを作成できる。現場資料で根拠を確認できた要点を候補とする。

現場資料は UTF-8 の `.md` / `.txt` を1件選び、原文の該当箇所を選ぶ。原本はブラウザーで開き、その場で原本を別途保存できる。資料の識別子は原本の SHA-256 から生成する。資料の版とページ・節等の参照箇所は担当者が指定する。出典は「現場資料」と明記し、出典情報と確認した要点を「現場資料に基づくノウハウ」に追記する。Markdown保存時に、既存の索引が扱える形式で現場資料の出典IDを付与する。元のカードの行と既存の出典を保持する。原本や未採用の抜粋は作業記録へ含めない。

現場資料用のAI機能を別途有効にした環境では、担当者が送信可否を確認してから、選んだ箇所、担当者の確認テーマ、資料表示名、確認日を既存の書き換え案APIへ送り、要点の案を得る。原本ファイル、他の箇所、URL、実カードID、カード本文は送らない。現場資料の節は、通常のカード書き換えの参考文脈からも外す。要点を編集して原文と照合し、差分を確認した後に反映する。現場資料の要点は現場での観測として整理し、公式の安全要件・作業基準・法令との照合は担当者が行う。保存形式は下書きMarkdownとJSON作業記録。実資料の共有保管・自動収集・検索公開は運用条件を決めてから接続する。

## カードを一括照合

> 最終検証: 2026-11-14 — 確認操作と「KB確認に基づく追記」への差し込み規則を、単体テスト・画面の静的描画テスト・型検査・ビルドで確認。実機の画面は未確認。

管理者向けの `/admin/knowledge/research` で、選択したMarkdown 1枚のタイトル、機種、本文の未確認事項や数値から照合の質問候補を作る。候補作成はブラウザー内で行う。担当者は質問文、送信対象、照合先を確認・変更できる。送信前に技術KBと法令KBへの予定回数を表示し、「照合する」を押したときだけ既存の検索APIへ質問文を送る。質問は既存のチャット履歴に保存される場合がある。

- 照合は最大2件ずつ実行する。進捗を表示し、中止や照合先ごとの再試行を受け付ける。認証切れのときは残りの送信を止める。技術KBと法令KBの回答・出典は分けて表示する。
- 選んだ照合先の応答が揃った質問ごとに、回答の抜粋・出典・確認日を定型の追記案にする。資料なし、条件の聞き返し、出典なしも区別する。AI の回答には「AI が KB を検索した結果です。出典を確認してから追記してください。」と注記する。
- 人の作業は確認だけにする。管理者が追記案ごとに回答の要点と出典（資料名・ページのリンク）を見て、「確認して追記する」か「追記しない」を選ぶ。既定は未選択（未確認）で、文言の書き直しは必須にしない。画面は「3. 確認する」の段階で「5件中 2件を追記・1件を追記しない・2件が未確認」のように件数を出す。未確認が残っていても差分と保存へ進めるが、未確認・追記しないものはカードに入らない。「本文に反映」は、確認して追記するものが1件以上あるときだけ押せる。差分を確認してから編集中の本文に反映する。
- AI の照合結果は、管理者が確認したものだけを「KB確認に基づく追記」に入れる。未確認・追記しないものはカードに入れない（「KB照合メモ（原資料未確認）」の節は作らない）。追記には確認日と「確認: 管理者が出典を確認（YYYY-MM-DD）」の1行を付ける。出典が1件も無い結果も、確認すれば記録として入れられる。照合した全ての照合先が資料なしのときは「KB に該当資料なし（確認日）」、聞き返しや出典のない回答を含むときは「根拠になる出典が見つからなかった（確認日）」と書く。どちらも未確認事項の解消ではなく確認した記録で、画面でも出典つきと区別して表示する。
- 差し込み規則: 「KB確認に基づく追記」の中身が情報の無い書き置き（「（該当なし）」「（なし）」「（Lists のみ）」「（該当 KB なし）」「（未実施）」など）なら置き換え、見出しに付いた同様の注記を外す。「（未実施 — SUE-3-17 本文…確定後。）」のように情報のある書き置きや既存の追記は消さず、その後ろに足す。同じ質問と確認日の組は二重に入れない（旧版の未確認メモ節にある同じ追記も含む）。節が無ければ「## 正式資料…」（見出しの揺れを含む）の前、それも無ければ末尾に作る。CRLF とコードフェンス内の見出しを保ち、frontmatter は変えない。`card_version` と `review_status` は上げず、技術承認はしない。追記時は既存の本文の主張、適用条件、カードの版を保持する。反映後の編集候補は既存のMarkdown保存機能から下書きとして取り出す。出力する下書きの公開・承認状態は既存の保存ルールに従う。ファイルの切替や本文の変更後は、旧本文への照合結果をそのまま採用できない。

## AI による本文の書き換え案

> 最終検証: 2026-11-14 — frontend の単体テスト・ローカル e2e（モック API）で確認。実 API・実機は未確認

一括照合の手順「3 確認する」の中に、管理者が確認した根拠だけを材料に、AI がカード本文の書き換え案を作る機能を足した（開発中）。API は別文書 [knowhow-rewrite-proposal-contract.md](./knowhow-rewrite-proposal-contract.md) を参照する。

* **表示条件**: `NEXT_PUBLIC_ENABLE_KNOWHOW_REWRITE=true` のときだけ。未設定なら何も出さない。`knowledge_id` を持つカードにだけ出す。
* **材料**: 「確認して追記する」を選んだ質問のうち、**出典つきの照合先の結果だけ**（質問・技術KB/法令KB・確認日・回答の先頭・出典の資料名とページ）。未確認・追記しない・出典なし・「該当なし」は送らない。frontmatter とカード全文も送らない。確認済みで出典つきのものが 1 件以上あるときだけ「AI に本文の書き換え案を作らせる」を押せる。実行前に、根拠の件数、書き換え対象と文脈として参照する節の数、カードIDと版を送ること、AIの利用料がかかることを表示する。
* **対象**: 「統合した回答・ノウハウ」「調査・確認手順」「未確認事項」の 3 節だけ（カードにあるもの）。上限を超える節・空の節・同名が複数ある節は、切り詰めず対象から外して理由を画面に出す。それ以外の節は読むだけの context として送る。
* **節ごとの確認**: 変更前後の差分・変更理由・使った根拠（確認済みの結果へのページ内リンク）・警告を出し、節ごとに「確認して反映する」「反映しない」を選ぶ。既定は未選択で、何も入らない。変更なしの節と、検査で不採用の節は本文を出さない。応答はクライアントでも再検証し（見出し・根拠番号・本文の構造・文字数）、外れた節は不採用にする。
* **食い違い**: カードと根拠の食い違いは別枠に出し、「未確認事項に追加する／しない」を選ぶ。追加するのは要確認の定型 1 行だけで、本文の主張は変えない。
* **反映**: 選んだ節の本文だけを置き換える（見出し・他の節・frontmatter・改行コード・コードフェンスは保つ）。案を作った時点から対象の節が編集されていたら、その節は反映せず「本文が変わったため、もう一度案を作ってください」と出す（人の編集を消さない）。手順「4 差分を確認」では、節の書き換えと既存の追記を 1 つの差分にまとめ、「本文に反映」で入る。どちらか一方だけでも進める。差分を表示したあとに書き換えの選択を変えた場合は、差分を作り直す。
* **案の破棄**: 確認の選択を変えた・照合を再試行した・質問を変えた・対象の節や根拠が変わった・別のカードを読み込んだときは、作った案を破棄して一言表示する。案・本文・回答は `console` にも localStorage にも出さない。
* **注意書き**: 反映する節が 1 つ以上あるとき、「本文の主張を変えました。Git に入れるときは card_version を上げ、台帳を作り直してください。この確認は技術承認ではありません。」を出す。frontmatter は自動では変えない。
* **検査**: サーバーと画面の両方で案を検査し、疑わしい案は不採用にする（案が出ないだけで、カードには入らない）。元の本文にも確認済みの根拠にも無い「数字＋単位」・資料番号・法令番号、元の本文に無いリンク・HTML、見えない文字・制御文字、見出しの行、閉じていないコードの囲みを含む案が対象。単位の無い 2 桁以上の数字は警告を付けて見せる。検査は文字の一致までで、意味の正しさは管理者の確認による。
* **差分の表示**: 変更された行は、行の中で変わった部分だけを色で強調する（1 行 400 字を超えるときは行単位の表示に戻す）。
* **未配備**: API（Lambda）は AWS に未配備。画面はモック API でのみ確認している。

## 出典と編集

技術資料は既存の認証付き`/doc`経由で開く。S3の署名付きURLを持ち帰りファイルやリンクへ残さず、S3 URIへ戻して中継する。法令は応答にある法令名・条文・施行日・e-Gov出典を表示し、HTTPSのe-Gov法令URLだけを有効にする。日付や条文番号、リンクのアンカーを推測しない。API応答の生HTML・埋込・画像を実行しない。

生成するMarkdownの技術資料URIと対象ノウハウIDは、バッククォートを含む値でも文字通りのコードとして保持する。値をHTMLや画像・リンクの構文として展開しない。アプリのプレビューだけに依存せず、持ち帰り先のMarkdownでも同じ境界を保つ。

「編集案へ取り込む」で、選択した回答と出典を調査メモとしてローカルMarkdown本文へ追記する。これはAI回答の採用候補であり、技術承認・法的判断・KB本文の人手確認ではない。照合済みチェックを自動で付けない。本文編集と同じ版失効を通し、OneNote案との再照合を必要にする。元ファイル・OneNoteへ自動書込みしない。

取り込み先は検索開始時の文書セッション・ID・原版・本文の作業版へ紐付ける。文書の再取込・別文書への切替・本文の手編集後は旧結果を表示できても取込み不可とし、再検索を案内する。ファイル未選択での調査は閲覧用であり、後から選んだファイルへ無警告で適用しない。同一検索の技術・法令両メモを順に追加する操作は許容し、その既知の追記だけでは相手側の結果を失効しない。取り込み先の条件を変える本文手編集は必ず失効させる。

調査メモには検索モード・質問・クライアント受信日時、APIが返す回答日時（有効な場合）、sessionId/messageIdも追跡情報として残す。これらはAI回答の追跡用であり、資料の改訂版や技術承認の識別子ではない。API履歴は60日で失われ得るため、採用時の本文と出典も併せて保持する。

### 担当者による照合まとめ

同じ質問・対象本文で得た両方の回答を、担当者が「一致している / 条件が違う / 食い違いあり / 判断保留」に整理できるようにする。初期値は判断保留。これはAI回答の比較メモであり、原資料本文の確認・技術承認・法的判断として扱わない。

- 比較して分かったことと適用条件・対象外を必須入力とし、それぞれ4000文字まで。判断保留・食い違いありの場合は未確認事項・次に確認することも必須。いずれの文章も自動生成・自動送信しない。
- 同じ質問のnormal/law各1件で、両方が根拠リンクを持つ回答の場合にだけ保存可能。片側失敗・未収載・聞き返し・別質問・別文書・手編集後の旧回答は使わない。
- メモは回答ペアと対象本文の版に紐付ける。再検索・文書再取込・本文手編集で以前の入力・取り込み済み表示を破棄し、新しい回答へ持ち越さない。片側の回答が更新されても同様。
- 「照合まとめをMarkdownへ取り込む」で、入力した比較内容・条件・保留事項と、両回答の本文・出典・追跡情報をローカルの修正候補へ追記する。未知の項目を「なし」「解決済み」と補完しない。Markdown構文やHTMLを入力しても構造の外へ実行・展開しない。
- 親の編集状態への追記成功を受け取ってから取り込み済みと表示し、同一内容の重複クリックを防ぐ。入力変更後は別の作業メモとして再取込み可能。追記失敗時に取り込み済みと表示しない。
- 既存の本文編集と同様、KB手動確認・OneNoteの確認/コピー状態を失効させる。本文へメモを追記しただけでは、食い違いの解消・公開・承認を成立させない。

`buildComparisonNote({technical, law, assessment})`を純粋関数として実装し、型付きの`assessment`は`status: consistent|conditions_differ|conflict|unresolved`、`findings`、`applicability`、`unresolvedPoints`を持つ。UIは既存の文書対象キーを使い、親への`onAdopt`が返す成功/失敗を確認する。

### 2026-10-30 ローカル先輩チャットのブラウザー一気通貫検証

`cd frontend && npm run test:e2e:local`は、PlaywrightのChromiumからNext.jsの`/knowledge/chat`を開き、テスト専用のloopback HTTP APIへ接続する。APIは合成質問・合成出典・履歴だけをメモリ内に持ち、検索・根拠判定・回答生成・保存もAPIモックが模擬する。Python Lambdaや本番検索・状態遷移のE2Eではなく、画面とHTTP契約の検査であり、認証・認可の証明ではない。Bedrock・DynamoDB・S3・Cognitoには接続しない。Playwright実行プロセスに限って`NEXT_PUBLIC_SKIP_AUTH=true`と`NEXT_PUBLIC_DEV_ADMIN=true`を渡す。

技術・法令の2レーン送信、送信中の入力停止、合成資料の出典表示、履歴一覧からの再読込、根拠0件、両レーン検索失敗時のエラー表示、モバイル/デスクトップ幅の横はみ出しなしを確認する。単体API契約ではユーザー所有権と管理者ゲートを別途検査する。実Lambdaの起動、Cognito認証、DynamoDB保存/削除/TTL到来、AWS IAM、実検索品質、社内資料の業務受入はこのブラウザー試験の対象外。
