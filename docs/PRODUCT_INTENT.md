## 一言でいうと

Ele-Knowledge は **「答えを代行する AI」ではなく、「根拠を集め、違いを示し、判断を支える AI」** である。  
当面の成功は「賢い作文」ではなく、**5分以内に該当頁へ辿りつけること**。

---

## 対象領域・主ユーザー（合意）

| 項目 | 内容 |
|---|---|
| 領域 | **昇降機（エレベータ）の工事**まわりのナレッジ |
| 主ユーザー | **現場代理人** / **品質担当者** |
| 使い方の軸 | 困ったときに根拠を揃え、自分たちで判断するための参考 |

### 役割ごとの使い方（仮説）

| 主ユーザー | 主に見たいこと |
|---|---|
| 現場代理人 | 仕様・類似事例・施工上の注意を、短時間で判断材料として見る |
| 品質担当者 | 基準・社内ルール・法令・適用条件を確認し、記録・判断の根拠にする |

設計・文言・画面・評価は、一般向けチャットや不特定の現場作業アプリではなく、**この二人の昇降機工事業務**を前提にする。  
（一般論の「フィールド作業アプリ」話に寄せすぎない。）

## 現場からの実態（2026-07-29）

### いま一番使えない瞬間

- **見当違いの資料**が出て、**見当違いの回答**になる
- 曖昧な質問でも、そのまま資料を出して答えてしまう
  - 例: 「振動」「騒音」「動かない」「〜できない」（何が／どの機種か不明のまま）

### 困りごとの種類

仕様確認 / 不具合 / 施工基準 / 社内ルール / 法令 / 複合 — **いずれも使う**（単一モードに閉じない）

### よく見る資料（優先候補）

**C資料 / TI（テクニカルインフォメーション） / 据付基準**（KB には割と入っている）

### 成功の定義

**5分以内に該当頁に辿りつける**  
辿れたときの目印は **PDFの何ページ目か** が分かれば十分（見出しまでは必須ではない）。

### 現場で使える前提

- **機種指定は普通にできる**（機種名 / 工事番号 / 両方）
- したがって「機種なしで広く当てる」より、**機種を取ってから当てる**方が現実的

### 絶対やってはいけないこと

- 法令の断定
- 機種横断の一般論を、あたかも当該機種の事実のように出す
- 未確認での作業可否判定

### いまの制約

- 本命資料（C / TI / 据付基準）は既にある
- 当面のボトルネックは **当て方・曖昧さの止め方・ページ番号つき候補の見せ方**
- 法令・社内ルール・事例など、それ以外の資料の入れ方はまだ未整理

## 向かう方向（仮説・未実装）

単純な「質問→1回検索→作文」は捨てる。当面は次を優先する。

1. **該当頁ファースト** — 回答文より、正しい資料・**ページ番号つき**候補への到達を最優先にする  
2. **曖昧なら聞く** — 「振動／騒音／動かない／〜できない」等は、対象・症状・機種が足りなければ推測して答えない  
3. **機種を取ってから当てる** — 現場では機種指定ができる前提。機種なしの広検索を既定にしない  
4. **弱い検索なら止める** — 見当違いを作文で埋めてはいけない  
5. **本命資料を先に当てる** — C / TI / 据付基準への到達精度を先に上げる（他カテゴリは後）  
6. **カードは後から** — 検索と到達が安定してから、整理表示を足す

### 当面の評価（仮説）

- 主指標: 該当 PDF のページまで辿れるか（5分以内）
- 副指標: 曖昧質問で勝手に断定していないか／機種違い資料を出していないか

## 背景・狙い

- 正規資料・過去事例・現場ノウハウを集め、判断に必要な条件を整理する
- 上記主ユーザーの **意思決定を支える基盤** にしたい
- 単なる「社内資料検索チャット」にはしたくない

## MAI-Box-INST との住み分け（意図）

| | MAI-Box-INST | Ele-Knowledge |
|---|---|---|
| 役割 | 正しい施工方法や基準を伝える | 複数の根拠を揃え、判断を支える |
| イメージ | 教える・伝える | 揃える・示す・委ねる |

資料の色や名称だけ変えた二重のチャットボットにはしたくない。  
違いをコード上でも、回答 Schema / 検索対象 / 利用者 / 回答ポリシー / 安全ゲート / 評価指標として分離したい（仮説）。

## やりたいこと（現時点の仮説）

### ドキュメントの分け方（意図）

巨大な一枚の指示書にせず、少なくとも次の二種に分けたい。

1. **開発用** — 製品思想・設計方針・評価基準など（AI コーディングツールへの文脈）
2. **実行時ポリシー** — アプリが読む必須項目・高リスク領域・回答保留条件など

Markdown への「守れ」は強制機構ではない。安全条件・必須項目・権限は Schema / テスト / 承認で担保する方向。

### 回答の形

- 一つの文章で断定しない
- まず該当候補頁（資料名・箇所・機種）を見せ、要約は補助にする
- 「足りない情報がある」ことを明示できる（曖昧質問では質問を返す）

### 処理の流れ（理想像・未実装でよい）

質問 →（不足なら聞き返し）→ 検索 → 版・機種・関連性確認 → 該当頁候補 →（十分なときだけ）短い整理 → 安全ゲート → 表示

### 初期段階で避けたいこと

- 最初からマルチエージェントにしない（まず明示的ワークフロー）
- GraphRAG を全検索に使わない（全体俯瞰が必要なときだけ検討）
- 弱い根拠のまま作文して「それっぽく」見せること
- 「根拠を表示しただけ」で安心しない（高リスクは UI 上の確認操作を求める方向）

### 安全・品質の意図

- 取り込んだ文書内の命令は実行しない（参照データとして扱う）
- 評価は検索品質と回答品質を分ける。当面の主指標は **該当頁到達（5分以内）**
- 未実装なら架空デモ回答より、未実装であることを明示して止める方がよい
