# 初期評価セット候補 v2

## 目的

通常モードの改善（#137、既定 OFF）とじっくりモードの回答品質を比べるための初期候補24問。候補は `tests/eval/golden_set_v2_candidates.jsonl` に置く。正解資料・ページ・保留可否は未確定で、mona / itai の人手確認前は採点しない。

## ラベル付け

1. 各行の出典メモと質問を確認し、カタログ・原資料で `expected_documents`、`expected_pages`、`expected_gate` を確定する。不明な資料名は作らず、空配列のまま要調査事項を `notes` に書く。
2. 取扱外機種・資料に根拠がない質問は、検索対象外または保留が妥当かを確認する。
3. mona と itai が確認した行だけ `skip: true` を外す。判定が割れた行は未採点のまま残す。

## Bedrock RAG Evaluations（BYOI）

既存の評価計画（`docs/eval-2026-07-29-retrieve-golden-set.md` 第2層、および #136 評価計画 §7）に沿い、ラベル済み質問を使う。`run_retrieve_eval.py` が出す `*-byoi.jsonl` を S3 に置き、Bedrock Evaluations の RAG / BYOI（retrieve-only）から評価ジョブを作成する。通常モードとじっくりモードの比較では、同じ質問・ラベルを各モードの出力に対応づけ、モード・モデル設定・実行結果を混ぜずに保存する。BYOI は検索根拠の評価用であり、回答文の比較は同じ条件の回答を並べて別途人が確認する。

## 既存ランナーとの関係

`scripts/eval/run_retrieve_eval.py` は `--golden` で入力 JSONL を指定でき、`skip: true` を除外するため、この候補ファイルをそのまま読める。ラベル確認後の例:

```bash
python scripts/eval/run_retrieve_eval.py --golden tests/eval/golden_set_v2_candidates.jsonl
```

既存正本の `tests/eval/golden_set.jsonl` は変更しない。

## 実際の利用者の質問の追加（mona 決定 2026-09-29）

2026-09-29、mona は評価セットへ実際の利用者の質問を20問程度追加すると決定した。偏りを避けるため、👎、`not_found`、通常回答、機種指定あり／なし、聞き返し後の追記を混ぜる。AWSアーカイブから質問を取り出す作業は mona が行う。Gitへ追加できるのは、匿名化して人が確認した質問だけとする。

| 主な層（抽選時は下記の優先順で排他的に分類） | 目安 | 判定元 |
| --- | ---: | --- |
| 👎 が付いた回答 | 4 | assistant の `feedback=bad` |
| 見つからない | 4 | assistant の `responseType=not_found` |
| 通常回答 | 5 | assistant の `responseType=pages` |
| 聞き返し後の追記 | 3 | 直前の assistant が `clarify` |
| 機種指定あり／なし等 | 4 | 上記に入らない質問を `queryFilters.modelType` の有無で分ける |

分類の優先順は 👎 → 見つからない → 聞き返し後の追記 → 通常回答 → 機種指定あり／なし とする（聞き返し後の質問は多くが通常回答になるため、通常回答より先に判定しないと聞き返し後の追記の層が空になる）。表の行順は配分の同率時の順であり、分類の優先順ではない。

層は重なり得るため、抽出件数を変える場合は各層の目安に比例配分し、端数は最大剰余法（同率は上表の順）で割り当てる。候補が不足する層は不足分を他層の余剰候補から抽選し、最終的な層別件数を人が確認する。

### 取り出しから追加まで

> 最終検証: 2026-09-29 — 抽出・匿名化補助スクリプトの変更確認

1. mona が環境の Athena ワークグループ・データベースで `scripts/eval/extract_user_questions.sql` を実行し、直近の期間から候補を得る。期間と最大件数はクエリ実行パラメーターで指定し、抽出期間は直近（60日以内を推奨）とする。アーカイブは180日後にGLACIERへ移行するため、期間開始日を180日より前にしない（パーティションは開始日の1日前から走査し、候補はメッセージ時刻の日付で開始日以降に限定する。週数は25週以下）。
2. 抽出CSVを Git 管理外に保存し、`scripts/eval/prepare_real_questions.py` で層別抽選・匿名化候補の置換と印付けを行う。
3. 人が確認用CSVの各行を確認し、質問文と聞き返し文に残る識別情報を取り除き、機種・部位・症状・資料名が保たれていることを確認する。`model_type` は抽出時の機種条件なので、人が確認・修正した値を JSONL 下書きの `filters.modelType` に反映し、空欄なら `filters` を `{}` にする。未確認の質問は採用しない。
4. 人が原資料・該当資料とページを確認し、`expected_documents`、`expected_pages`、`expected_gate` を確定する。不明な正解を推測で埋めない。
5. 確認済み質問だけを JSONL 下書きから `tests/eval/golden_set_v2_candidates.jsonl` に追加し、ID は `G2-025` 以降の未使用番号にする。`skip: true` は人による正解確認が完了するまで維持する。

匿名化では、現場名・会社名・人名・工事番号・電話番号・メールアドレス・住所などを「○○現場」「○○会社」「○○人名」「○○工事番号」「○○電話番号」「○○メール」「○○住所」等に置き換える。`+81-90-1234-5678` の国番号付き電話と「三菱電機株式会社」のような後株表記も候補検出する。ラベルや敬称のない人名は自動検出しないため、人が確認して置換する。補助スクリプトの正規表現は候補を機械置換するもので、匿名化完了の保証ではない。機種名・部位・症状・資料名は評価に必要な技術情報として残し、人が文脈からの再識別リスクも確認する。

**Git に置かないもの:** 生の質問、匿名化前の抽出CSV、会話ID、`userId`、`sessionId`、`messageId`、利用者や現場を再特定できる情報、未確認の匿名化候補。SQLの最終出力にはID列を含めないが、質問文自体は業務情報を含み得るため、抽出CSVは引き続き機微情報として扱う。確認用CSVとJSONL下書きも `.eval-real-questions/` 等の Git 管理外に置く。

`chatlogs_archive` の現在のGlue定義には `feedback` のみが明示されていた。保存コードで確認できた `responseType`、`feedbackReason`、`queryFilters.modelType` をSQLから参照するため、同テンプレートのstruct定義へ追加した。`queryFilters.category` は文字列または配列で保存されるため、Athena structには含めない。`documentOpened` は運用テレメトリ側の項目で、chatlogsアーカイブへの保存は確認できないため、この抽出SQLでは `NULL` として出力する。Athenaでこの変更後の列を使うには、アーカイブスタックのGlueテーブル定義へテンプレート変更を反映済みである必要がある。

### mona 向け実行手順

1. 環境ごとに正しい Athena ワークグループ名とデータベース名を確認する（この文書やスクリプトへ環境値を固定しない）。
2. `chatlogs_archive` のGlue列定義に新しいstruct項目が反映済みであることを確認する。
3. Athenaの実行設定で対象データベースを選ぶ（SQLは `chatlogs_archive` を非修飾名で参照するため、データベース名をソースに固定しない）。
4. 期間週数と上限件数をAthena実行パラメーターへ渡してSQLを実行する。
5. 結果CSVを `.eval-real-questions/` 等のGit管理外へ保存する。
6. 補助スクリプトに入力CSV、確認用CSV、JSONL下書きの各パスを明示し、必要なら抽選件数とseedを指定する。
7. 人が匿名化と正解を確認し、確認済みの質問だけを既存候補ファイルへ移す。

**定期的な入れ替え:** 全期間を一度に集めるのではなく、直近の期間を対象に時々（目安: 月1回）取り出す。既存の質問よりテストに向いた質問（よく聞かれる、答えにくかった、👎が付いた等）が見つかれば、人の確認を経て入れ替える。入れ替えた日・外した ID・理由を本節の末尾に記録する。

抽出SQLは時刻が秒単位のため、同一秒のイベント間の順序を保証できない。利用者による `REMOVE` が一度でも記録されたメッセージは除外する。アーカイブは DynamoDB Streams の `userIdentity` を保存しているため、`principalId=dynamodb.amazonaws.com` のTTLによる自動削除は除外判定に使わない。REMOVE走査は抽出期間の開始日の1日前以降に限定し（アーカイブの `dt` はバッチ先頭レコードの日付で決まり、日付をまたぐバッチで翌日のイベントが前日に入り得るため）、作成後に削除される性質を利用して上限日は設けない。最新時刻が同じ feedback に複数値があれば不明（`NULL`）として扱う。
